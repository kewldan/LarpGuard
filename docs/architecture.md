# bot-shield: архитектура

Статус: черновик v0.1 · 2026-10-18

bot-shield — self-hosted шлюз для фильтрации ботов, скрепинга и прочей
автоматизации. Основной метод — отпечатки клиента на уровнях TCP, TLS, HTTP и
JS и проверка их согласованности с тем, кем клиент себя заявляет. Шлюз также
отвечает за rate limiting. Встаёт перед существующим Traefik без изменений в
его конфигурации и лейблах контейнеров.

## 1. Цели и рамки

### Цели

- Отличать браузеры людей от автоматизации: HTTP-библиотек, headless-браузеров,
  impersonation-клиентов (`curl-impersonate`, `tls-client`), скреперов.
- Ограничивать частоту запросов по гибким ключам (IP, подсеть, ASN, отпечаток,
  сессия, API-ключ) с порогами, зависящими от скора.
- Встраиваться перед уже работающим Traefik **без правок лейблов и роутеров**.
- Пропускать «хороших» ботов (поисковики, мониторинг, партнёров) после проверки
  подлинности.
- Отдавать приложениям сигнал (`X-Bot-Score`), чтобы они могли принимать свои
  решения.
- Иметь shadow mode: наблюдать без вмешательства и калибровать пороги.

### Целевые нефункциональные параметры

| Параметр                         | Цель                                   |
|----------------------------------|----------------------------------------|
| Пропускная способность узла      | 20–50k RPS, 50–100k одновременных соед.|
| Добавочная задержка (p99)        | ≤ 2 мс на запрос без челленджа         |
| Новые TLS-хендшейки              | ≥ 5k/с на узел (ECDHE, 8 ядер)         |
| Доступность                      | fail-open: отказ шлюза ≠ отказ сайтов  |
| Применение изменений политик     | ≤ 5 с без перезапуска                  |

Цифры — ориентиры для проектирования, уточняются нагрузочными тестами.

### Не цели (на v1)

- Multi-tenant SaaS: один владелец, одна инсталляция (ADR-006).
- WAF (SQLi, XSS и т. п.) — отдельная задача.
- Защита от объёмного L3/L4 DDoS — это уровень провайдера или CDN. Шлюз
  защищает себя лимитами соединений, но не пропускную способность канала.
- Мобильный SDK с аттестацией устройства — возможное расширение (раздел 16).
- HTTP/3 (QUIC) на входе — с M6, выключено по умолчанию (ADR-011).

## 2. Топология и встраивание

```
                         ┌────────────────────────── хост ──────────────────────────┐
                         │                                                          │
 Internet ──► :80/:443 ──┤ bot-shield (network_mode: host)                          │
                         │   ├─ L4-классификатор (peek ClientHello)                 │
                         │   │    ├─ ALPN acme-tls/1 ────────────── L4 passthrough ─┼─┐
                         │   │    ├─ нет сертификата для SNI ────── L4 passthrough ─┼─┤
                         │   │    └─ host с policy=passthrough ─── L4 passthrough ─┼─┤
                         │   ├─ TLS-терминация (серты из acme.json)                 │ │
                         │   ├─ сигналы → скоринг → действие → rate limit           │ │
                         │   └─ upstream: HTTPS, тот же SNI/Host ───────────────────┼─┤
                         │                                                          │ ▼
                         │ Traefik 127.0.0.1:8443 / :8080  (роутинг, ACME, лейблы) ─┼──► сайты
                         │                                                          │
                         │ Valkey (опц.) · NATS · ClickHouse                        │
                         └──────────────────────────────────────────────────────────┘
```

Что меняется в Traefik:

1. `entryPoints.web` и `entryPoints.websecure` переезжают на `127.0.0.1:8080` и
   `127.0.0.1:8443` (или на внутренний адрес docker-сети).
2. В entrypoint'ах включаются `proxyProtocol.trustedIPs` и (на
   `websecure`) `forwardedHeaders.trustedIPs` с адресом bot-shield.
   Passthrough-соединения и порт 80 приходят с PROXY protocol v2.
   Терминированные запросы идут по пулу HTTP/2-соединений без PROXY и несут
   адрес клиента в `X-Forwarded-For` / `X-Real-IP`, которые шлюз выставляет
   сам, вырезая присланные клиентом (ADR-015). Traefik применяет PROXY,
   только если тот пришёл, поэтому оба вида соединений живут на одном
   entrypoint (проверено на Traefik v3.5). Пример — `deploy/traefik.yml`.
3. Сертификаты, ACME-резолверы, роутеры, middleware и лейблы остаются как есть.
   Добавляются TLS-опции из `deploy/traefik-tls.yml` (`sniStrict` и
   отдельная опция `passthrough@file` для роутеров passthrough-хостов) и
   редирект `web` → HTTPS — иначе passthrough-соединения и порт 80 обходят
   проверки шлюза (раздел 11.1).

Что делает bot-shield:

- Читает `acme.json` Traefik (read-only mount) и опрашивает его на изменения
  (по умолчанию раз в 2 с). Traefik продолжает выпускать и продлевать сертификаты (ADR-003).
- Пробрасывает трафик в Traefik повторно по TLS с тем же SNI, поэтому роутеры
  с `tls=true` на `websecure` работают без изменений (ADR-004).
- HTTP-01 на :80 проксирует в Traefik как есть. ClientHello с ALPN `acme-tls/1`
  (TLS-ALPN-01) отдаёт Traefik на уровне L4.
- Для SNI, которого нет в `acme.json`, делает L4 passthrough только с
  IP-лимитами. Новый сайт не сломается до появления сертификата, а после
  перечитывания `acme.json` сразу попадёт под защиту. ClientHello без SNI по
  умолчанию отклоняется (`no_sni: reject`): Traefik маршрутизирует HTTPS по
  `Host`, и такое соединение дошло бы до защищённого сайта мимо проверок.
- Слушает docker socket (read-only), как и Traefik, и берёт политики из лейблов
  `botshield.*` (раздел 9).

## 3. Компоненты

### 3.1. Data plane (C++20, один процесс `bot-shield`)

Модель: thread-per-core, `SO_REUSEPORT` на каждый воркер, без разделяемого
изменяемого состояния в горячем пути. Каждый воркер владеет своими
соединениями, шардом rate limiter и локальными кешами. Межпоточный обмен идёт
через lock-free очереди и RCU-снапшоты конфигурации (ADR-002).

| Модуль                 | Ответственность                                                         |
|------------------------|-------------------------------------------------------------------------|
| `net/listener`         | accept, `TCP_SAVE_SYN`/`TCP_SAVED_SYN`, лимиты соединений на IP          |
| `net/l4_classifier`    | чтение и разбор ClientHello до TLS, выбор: терминировать или passthrough |
| `net/splice`           | L4 passthrough, PROXY protocol v2 (см. ниже); `splice(2)` — оптимизация на потом |
| `tls/terminator`       | BoringSSL, выбор сертификата по SNI, сессии/тикеты                       |
| `tls/cert_store`       | загрузка `acme.json`, опрос изменений, атомарная подмена снапшота        |
| `http/h1`              | llhttp, сохранение исходного порядка и регистра заголовков               |
| `http/h2`              | nghttp2, перехват SETTINGS / WINDOW_UPDATE / PRIORITY / порядка псевдозаголовков |
| `signals/*`            | сборщики сигналов: tcp, tls, h2, headers, reputation, behavior           |
| `fp/library`           | библиотека известных клиентов, проверки согласованности                 |
| `score/engine`         | взвешенные сигналы → скор + коды причин, затем правила CEL               |
| `action/*`             | allow, tag, throttle, challenge, tarpit, block, decoy                   |
| `challenge/*`          | выдача и проверка JS/PoW-челленджей, подпись и проверка токенов          |
| `ratelimit/*`          | локальный GCRA, синхронизация с Valkey, строгий режим                    |
| `proxy/*`              | HTTP-aware прокси: HTTP/1.1 и HTTP/2 к клиенту, пул HTTP/2 к Traefik (ADR-015) |
| `events/emitter`       | компактные события запросов → NATS (с сэмплированием)                    |
| `config/*`             | YAML + docker-лейблы → снапшот политик, валидация, hot reload            |
| `admin/api`            | HTTP API на unix-сокете: статус, политики, allow/deny-листы, разбор решений |

**Про реальный IP клиента.** Traefik видит все соединения от bot-shield,
поэтому шлюз начинает каждое upstream-соединение с заголовка PROXY protocol v2
(адрес и порт клиента плюс TLV `PP2_TYPE_AUTHORITY` с SNI). На entrypoint'ах
Traefik для этого включён `proxyProtocol.trustedIPs`. Отключается в конфиге
(`traefik.proxy_protocol: false`), но тогда Traefik видит только 127.0.0.1.

### 3.2. Control plane

Отдельного сервиса на v1 нет: политики живут в YAML и docker-лейблах, а
`admin/api` встроен в процесс. Веб-UI (просмотр решений, allow/deny, графики)
появится позже как отдельное приложение поверх `admin/api` и ClickHouse.

### 3.3. Analytics plane

- **NATS JetStream** — буфер событий, развязывающий горячий путь и хранилище.
- **ClickHouse** — сырые события и агрегаты. Ingest через NATS table engine
  или маленький консьюмер.
- **Офлайн-задачи** (Python, по расписанию): кластеризация новых отпечатков,
  поиск аномалий, предложения правил, обновление `fp/library`, обучение модели
  (ONNX).

### 3.4. Состояние

- **Valkey** — распределённые счётчики rate limit, общие deny-листы, отзыв
  токенов. **На одном узле не обязателен**: всё работает в памяти (ADR-009).
- Локально в памяти: LRU-кеши репутации, поведенческие окна, снапшот
  библиотеки отпечатков, снапшоты IP-баз (ASN, датацентры, Tor).

## 4. Путь запроса

```
accept ─► TCP_SAVED_SYN ─► peek ClientHello ─► классификация
                                                  │
              ┌───────────── passthrough ─────────┤
              ▼                                   ▼
        splice в Traefik                   TLS handshake (BoringSSL)
        (только IP-лимиты)                        │
                                                  ▼
                                      HTTP/1.1 или HTTP/2 разбор
                                                  │
                         ┌────────────────────────┤ на каждый запрос:
                         ▼                        ▼
               служебные пути /__bs/*     сбор сигналов (conn-уровень кешируется)
               (челлендж, верификация)            │
                                                  ▼
                                    проверка токена __bs (если есть)
                                                  │
                                                  ▼
                                      скоринг → правила CEL → действие
                                                  │
                                                  ▼
                                    rate limit (ключи и лимиты по классу)
                                                  │
                     ┌──────────┬────────┬────────┼────────┬──────────┐
                     ▼          ▼        ▼        ▼        ▼          ▼
                   block    challenge  tarpit   decoy   throttle   allow/tag
                                                                      │
                                                                      ▼
                                      upstream в Traefik + X-Bot-Score/Reasons
                                                  │
                                                  ▼
                                       ответ клиенту, событие → NATS
```

Принципы:

- Сигналы уровня соединения (TCP, TLS, H2 SETTINGS) считаются один раз на
  соединение и переиспользуются всеми запросами в нём.
- В горячем пути нет синхронного сетевого I/O. Исключение — строгий режим rate
  limit для явно помеченных маршрутов (раздел 8).
- Решение детерминировано для одного снапшота конфигурации и состояния.
  `admin/api` умеет объяснить его по `request_id`.

## 5. Сигналы и отпечатки

### 5.1. Пассивные сигналы

| Уровень   | Что собираем                                                                 | Отпечаток            |
|-----------|-------------------------------------------------------------------------------|----------------------|
| TCP/IP    | TTL (с нормализацией к 64/128/255), window, MSS, window scale, порядок опций, DF, ECN | свой `tcp_fp` (+ JA4T, ADR-014) |
| TLS       | версия, cipher suites, порядок расширений, GREASE, supported_groups, sig_algs, ALPN, key_share, ECH | JA4 (+ JA3 для совместимости) |
| HTTP/2    | SETTINGS (порядок и значения), WINDOW_UPDATE, PRIORITY/priority frames, порядок псевдозаголовков | H2-fp (формат Akamai) |
| HTTP/1.1  | порядок и регистр заголовков, `Connection`, `Accept-*`                        | свой `header_fp` (+ JA4H, ADR-014) |
| Заголовки | `User-Agent`, `sec-ch-ua*`, `sec-fetch-*`, `accept-language`, `accept-encoding` | согласованность      |
| Сеть      | ASN, тип (датацентр, хостинг, мобильный, резидентный), Tor, известные прокси  | репутация            |

Форматы (реализация в `src/fp/`):

- `tcp_fp` — `<ip>:<начальный TTL>:<window>:<mss>:<wscale>:<опции>:<флаги>`,
  опции буквами в порядке на проводе, например `4:64:64240:1460:7:MSTNW:df`.
- `ja4` / `ja4_r` — JA4 по спецификации FoxIO (BSD-3), сверен с эталоном
  `t13d1516h2_8daaf6152771_e5627efa2ab1`.
- `h2_fp` — формат Akamai: `SETTINGS|WINDOW_UPDATE|PRIORITY|псевдозаголовки`,
  например `1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p`.
- `header_fp` — `<версия>:<число заголовков>:<sha256 имён по порядку, 12>`;
  регистр имён на HTTP/1.x сохраняется.
- `ja4t`, `ja4h` — только при сборке с `BOT_SHIELD_FOXIO=ON` (ADR-014).

HTTP читается пассивно: копия потока клиент → Traefik идёт в разборщик
(llhttp для HTTP/1.x, свой разбор кадров + HPACK из nghttp2 для HTTP/2).
Разборщик ничего не меняет и при любой ошибке, апгрейде (WebSocket) или
превышении лимитов (64 КБ заголовков, 128 запросов) просто отключается.

TCP SYN берётся через `setsockopt(TCP_SAVE_SYN)` на слушающем сокете и
`getsockopt(TCP_SAVED_SYN)` после `accept`. Для этого нужен Linux, а
контейнер должен работать в `network_mode: host`: при DNAT через docker-bridge
TTL уменьшается и часть картины искажается.

### 5.2. Проверки согласованности (основной метод)

`fp/library` хранит профили клиентов:

```yaml
- id: chrome-desktop
  ua_match: { family: Chrome, major: ">=120" }
  platforms: [Windows, macOS, Linux]
  ja4: ["t13d1516h2_8daaf6152771_*"]        # шаблоны
  h2: ["1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p"]
  header_order_h2: [":method", ":authority", ":scheme", ":path"]
  required_headers: [sec-ch-ua, sec-fetch-site, sec-fetch-mode, accept-language]
```

Проверки (каждая даёт код причины и вес):

- `ua_tls_mismatch`: UA говорит Chrome, а JA4 не из профиля Chrome.
- `ua_h2_mismatch`: H2 SETTINGS или порядок псевдозаголовков не совпадают с
  профилем.
- `os_tcp_mismatch`: UA говорит Windows, а TCP-стек похож на Linux.
- `missing_client_hints`: Chromium без `sec-ch-ua` на навигации.
- `fetch_meta_inconsistent`: `sec-fetch-mode=navigate`, но `accept` не HTML.
- `known_automation_fp`: JA4 или H2 из списка известных библиотек (Go
  `net/http`, Python `requests`/`httpx`/`aiohttp`, Node `undici` и т. д.).
- `impersonation_artifacts`: идеальный JA4 Chrome при нетипичном
  WINDOW_UPDATE или порядке заголовков (типично для `curl-impersonate`).

Нормальные расхождения (корпоративные TLS-прокси, антивирусы с MITM, старые
версии) снижают вес до «подозрительно», не до «бот». Для этого в библиотеке
есть профили `mitm-proxy-*`.

### 5.3. Активные сигналы (JS-челлендж)

Собирает скрипт челленджа (раздел 7):

- `navigator.*`: `webdriver`, `plugins`, `languages`, `hardwareConcurrency`,
  `deviceMemory`, `userAgentData` (сверка с заголовками).
- Отпечатки canvas, WebGL (vendor и renderer), audio, список шрифтов, метрики
  экрана. Каждый хешируется на клиенте и отправляется хешем.
- Маркеры автоматизации: следы CDP (`Runtime.enable`-побочки), Playwright,
  Puppeteer, `chrome.runtime` в headless, расхождение между main thread и
  Worker (`navigator` в Worker vs в окне).
- Тайминги: время выполнения PoW против заявленного `hardwareConcurrency`,
  джиттер `performance.now()`.

### 5.4. Поведенческие сигналы

`behavior/BehaviorStore` — общее для всех воркеров шардированное хранилище
(как у лимитов: соединения клиента попадают на разные воркеры). Клиент —
хеш JA4 + хеш подсети (/24, /48) + хост. Счётчики живут в окне
`behavior.window` (10 мин), потом начинаются заново; клиенты, которых не
было дольше окна, вычищаются; при `max_clients` новые не отслеживаются
(они считаются в `untracked()`). Каждый запрос классифицируется по
`Sec-Fetch-Mode`/`Sec-Fetch-Dest`, `Accept` и пути: навигация, API
(`cors`, `X-Requested-With`, `/api/`, `/graphql`, JSON), статика
(`script`/`style`/`image`/`font` или расширение). Сигналы (веса — в
библиотеке, вес 0 выключает):

| Сигнал | Условие |
|---|---|
| `behavior_regular_timing` (30) | 16 последних запросов, средний интервал ≤ 30 с, σ/среднее < 0,1 |
| `behavior_not_found` (30) | ≥ 20 запросов в окне, больше половины 404/410 |
| `behavior_api_without_page` (20) | ≥ 10 API-запросов и ни одной навигации и статики |
| `behavior_no_assets` (25) | ≥ 8 навигаций без статики на хосте, статика которого идёт через шлюз (её запрашивал хоть один клиент) |
| `behavior_sequential_ids` (35) | ≥ 10 шагов `/item/N` → `/item/N+1` подряд |

Проверенные краулеры поведенческие сигналы не получают. Позже: энтропия
путей, обход пагинации.

### 5.5. Хорошие боты

- Поисковики (Google, Bing, Yandex, Apple, Baidu, Petal, Seznam, Naver,
  Amazon): имя из User-Agent → reverse DNS адреса → имя должно быть в
  опубликованных доменах краулера (`googlebot.com`, `search.msn.com`,
  `yandex.ru` …, суффикс по границе метки) → forward DNS имени должен
  вернуть тот же адрес. Проверка идёт в фоновых потоках через системный
  резолвер; путь запроса только читает кеш (подтверждённые — 24 ч,
  провалы — 1 ч, по паре «краулер, IP»), поэтому первый запрос с нового
  адреса оценивается как обычный (`unverified_crawler`). Очередь и кеш
  ограничены.
- Подтверждённый краулер получает класс `verified_bot`, скор 0 и причину
  `verified_crawler:<id>`; действие — `policy.actions.verified_bot` (allow по
  умолчанию), лимиты можно задать по классу `verified_bot`. Токен челленджа и
  правила `score` его класс не меняют, правила `allow`/`block` и списки —
  меняют.
- Провал проверки — сигнал `fake_crawler:<id>` (вес `fake_crawler`, 70):
  подделка Googlebot сразу становится ботом.
- AI-краулеры (GPTBot, ChatGPT-User, OAI-SearchBot, ClaudeBot, Claude-User,
  CCBot, PerplexityBot, Bytespider, Amazonbot, cohere-ai,
  Meta-ExternalAgent, Diffbot и др.) узнаются по User-Agent, получают
  причину `ai_crawler:<id>` и действие из `crawlers.ai`
  (`default` — оценивать как всех, `allow`, `challenge`, `block`). Правила и
  списки главнее. Индексацию поисковиками можно оставить, а сбор данных для
  моделей — запретить.
- Позже: опубликованные IP-диапазоны (OpenAI, DuckDuckGo и др.), Web Bot Auth
  (HTTP Message Signatures), mTLS для партнёров. Свой мониторинг — правилом
  `allow` по CIDR или заголовку.

## 6. Скоринг и действия

### 6.1. Скоринг

1. Каждый сработавший сигнал добавляет вес и код причины.
   `score = clamp(Σ w_i, 0, 100)`.
2. Валидный токен челленджа понижает скор на величину, зависящую от его
   класса, но не обнуляет поведенческие сигналы.
3. Правила (свой язык условий, ADR-008) выполняются после скоринга:
   сначала все правила `score` корректируют оценку, затем первое
   сработавшее правило `allow` / `block` переопределяет действие класса.
   Режим shadow/enforce по-прежнему решает, выполняется ли действие.

   ```yaml
   rules:
     - name: monitoring
       when: 'cidr("10.0.0.0/8") and header("x-monitor") == "1"'
       action: allow
     - name: admin-scrapers
       when: 'path ~ "/admin*" and class != "human"'
       action: block
     - name: mobile-app
       when: 'ua_tool == "okhttp" and host == "api.example.com"'
       action: score
       score: -40
   ```

   Язык: строки, целые, `true`/`false`, списки строк; `==` `!=` `<` `<=`
   `>` `>=`, `~` (glob), `in` (в списке, в т. ч. `"x" in reasons`), `and`,
   `or`, `not`, скобки. Поля: `host`, `method`, `path` (без query),
   `http_version`, `sni`, `alpn`, `ja4`, `h2_fp`, `pseudo_order`,
   `header_fp`, `tcp_fp`, `user_agent`, `ua_family`, `ua_engine`, `ua_os`,
   `ua_tool`, `score`, `class`, `reasons`. Функции: `header("name")`,
   `has_header("name")`, `cidr("net/len")`. Типы проверяются при загрузке
   конфига (`--check-config`), совпадения попадают в причины как
   `rule:<name>`.

4. Модель (`model/`) даёт дополнительный сигнал `model` (вес 30), если
   её вероятность не ниже `model.threshold` (0,8). Модель советует, а не
   решает. Это градиентный бустинг на деревьях без внешних зависимостей
   (вместо ONNX Runtime): обучение — `tools/train_model.py` (numpy),
   вычисление — `GbdtModel` на C++ за микросекунды.
   - *Признаки* (`model/features.h`, набор `f1`, 40 штук): протокол и
     заголовки, что заявляет User-Agent (движок, мобильность), части JA4
     (TLS 1.3, число шифров и расширений, ALPN, SNI), TTL TCP, вид запроса
     (навигация, API, статика) и сигналы, которые не служат метками.
     Шлюз считает вектор для каждого оценённого запроса и пишет его в
     событие `req` (`features`, `model.log_features`), поэтому обучение
     видит ровно те же значения и код признаков не дублируется.
   - *Слабые метки*: «автоматизация» — `honeypot*`, `known_automation:*`,
     `fake_crawler:*`, `automation_user_agent`, `headless_user_agent`;
     «человек» — `token_valid` и выборка `class = human` со скором 0. Эти
     сигналы и признаки инструментов в вектор не входят, чтобы модель
     обобщала по стеку и поведению, а не повторяла метку.
   - *Формат*: JSON с `feature_set`, именами признаков, `base` и деревьями
     в массивах (`x < threshold` — влево, дети после родителя). Шлюз
     отказывается грузить модель для другого набора признаков. Совпадение
     предсказаний C++ и Python проверяет `tests/data/gbdt_fixture.json`.
   - В событии — `model_score`. Порог и вес стоит подбирать по нему в
     shadow mode.

Классы: `human` (< 30), `suspicious` (30–69), `bot` (≥ 70), отдельно
`verified_bot`. Пороги задаются на политику.

### 6.2. Действия

| Действие    | Поведение                                                                       |
|-------------|----------------------------------------------------------------------------------|
| `allow`     | проксировать, добавить `X-Bot-Score`, `X-Bot-Class`, `X-Bot-Reasons`             |
| `tag`       | как `allow`, но явно для shadow mode (решение пишется в событие как «would_X»)   |
| `throttle`  | применить пониженный лимит класса                                                |
| `challenge` | навигация (GET/HEAD с `Sec-Fetch-Mode: navigate` или `Accept: text/html`) → 403 и страница челленджа; иначе 403 + JSON `{"error":"challenge_required","challenge":"/__bs/challenge?r=…"}` |
| `tarpit`    | 200 и тело, которое капает по `tarpit.chunk` байт раз в `tarpit.interval` до `tarpit.duration` (16 байт/с, 30 с); больше `tarpit.max_active` одновременно — обычный блок. HTTP/1.1 и HTTP/2, ушедший клиент освобождает слот |
| `block`     | 403 (или 404 по политике), короткий ответ, отпечаток → кратковременный deny-кеш  |
| `decoy`     | 200 с правдоподобными фальшивыми данными: HTML для навигации, JSON для остального (встроенные шаблоны или `decoy.html_file`/`json_file`) с водяным знаком |

### 6.3. Honeypot и водяные знаки

- Пути-ловушки `honeypot.paths` (glob): по умолчанию то, что ни один сайт
  не отдаёт, а сканеры ищут (`/.env`, `/.git/*`, `/wp-config.php*`, …).
  `/wp-admin/` в список по умолчанию не входит — у WordPress-сайтов он
  настоящий. Сам запрос получает сигнал `honeypot` (100), а адрес и пара
  «JA4 + подсеть» помечаются на `honeypot.ttl` (1 ч): все их запросы на любом
  хосте получают `honeypot_client` (70). Метрика `honeypot_hits_total`.
  Позже: невидимые ссылки-ловушки, вставляемые в HTML.
- Водяные знаки для `decoy`: `{{watermark}}` в шаблоне заменяется на
  12 hex от HMAC(активный ключ токенов, `request_id`). Знак пишется в событие
  `req` (колонка `watermark`), поэтому найденные где-то данные приводят к
  запросу, его отпечатку и подсети без отдельного хранилища.

## 7. Челленджи и токен

### 7.1. Виды

- **Невидимый JS** — скрипт на странице собирает сигналы (5.3) и решает PoW.
  Без внешних ресурсов и без ввода от пользователя.
- **PoW** — hashcash: найти `counter`, при котором у
  `SHA-256("<nonce>:<counter>")` не меньше `D` ведущих нулевых бит. SHA-256 в
  скрипте на чистом JS: для миллионов коротких входов это быстрее WebCrypto
  (≈1 млн хешей/с на ядро). Сложность по классу: `suspicious` — 16 бит
  (≈65 тыс. хешей, ~0,1 с), `bot` — 19 бит (≈0,5 млн, ~0,5 с); настраивается.
- **Капча** — интерфейс плагина для стороннего провайдера, пока не сделан.

### 7.2. Поток

```
GET /page  ──► challenge ──► 403 + HTML/JS (no-store) с nonce и сложностью
                                   │
     браузер: сигналы + PoW        │ location.replace
                                   ▼
GET /__bs/verify?n=<nonce>&c=<counter>&s=<signals b64url>
                 ──► проверка ──► 302 → исходный URL, Set-Cookie: __bs=<token>
                              └─► 403 «не удалось проверить браузер»
```

- Nonce stateless: `n1.<issued>.<D>.<ja4 hash>.<ip hash>.<return path
  b64url>.<key id>.<HMAC>`, живёт 5 минут и привязан к тому же клиенту, что и
  токен. Путь возврата хранится в nonce и принимается, только если начинается с
  одного `/` (не `//`, не `/\`, без CR/LF): открытого редиректа нет.
- `GET` вместо `POST`, чтобы проверка работала без CORS и форм; ответ
  `no-store`, nonce одноразовым не делается (повтор в пределах 5 минут даёт
  тот же токен тому же клиенту, что безвредно).
- Проверка отклоняет: чужой или просроченный nonce (`bad_nonce`), смену JA4
  или подсети (`binding`), неверный PoW (`pow`), отсутствие сигналов
  (`signals`), `navigator.webdriver` (`webdriver`), глобальные объекты
  PhantomJS/Nightmare (`automation_globals`), бренд `HeadlessChrome`
  (`headless`), пустой `navigator.languages` (`no_languages`). Причина пишется
  в событие как `challenge:failed:<reason>`.
- `/__bs/challenge?r=<path>` отдаёт страницу по прямой ссылке: так её
  открывают SPA и API-клиенты из JSON-ответа (7.4).

Служебный префикс `/__bs/` резервируется на всех хостах и обрабатывается до
режима хоста (работает и при `off`).

### 7.3. Токен `__bs`

Stateless, проверяется без похода в хранилище:

```
v1 . issued . expires . ja4_hash[8] . ip_prefix_hash[8] . key_id . HMAC-SHA256[128 бит]
```

- Привязан к хешу JA4 и к /24 (/48 для IPv6). Смена TLS-стека или сети
  инвалидирует токен.
- TTL — `challenge.token_ttl` (12 ч по умолчанию). Ключи в JSON-файле
  `{"active": "k2", "keys": {"k1": "<base64>", "k2": "<base64>"}}` (секреты
  ≥ 32 байт): подписывает активный, принимаются все — ротация без разлогина.
  Без файла ключ случайный и токены не переживают рестарт (предупреждение в
  логе).
- Валидный токен снимает `challenge.token_credit` (40) баллов со скора, класс
  пересчитывается, в причины добавляется `token_valid`. Если правило или класс
  всё равно требуют `challenge`, клиент с токеном пропускается; `block` токен
  не отменяет.
- Cookie: `Secure; HttpOnly; SameSite=Lax; Path=/`. Шлюз вырезает `__bs` из
  `Cookie` перед отправкой в Traefik (пустой заголовок удаляется):
  приложение токен не видит.
- Отзыв массово — ротацией ключа. Точечный отзыв и детект шаринга токенов
  между ботами — в аналитике (M5).

### 7.4. Не-HTML клиенты

API, XHR и мобильные клиенты не могут пройти интерстишиал. Для них
`challenge` отвечает 403 с JSON и ссылкой на `/__bs/challenge?r=…`: SPA может
открыть её навигацией и вернуться с токеном. Токен, полученный при навигации
на сайт, действует и для XHR того же браузера. Чистые API защищаются
API-ключами (ключ лимита) и правилами `allow`, а не челленджем.

## 8. Rate limiting

### 8.1. Модель

- Алгоритм — **GCRA** (одна метка времени на ключ, ровная выдача, поддержка
  burst).
- Ключ — составной, задаётся в лимите: `ip`, `ip_prefix` (/24, /48), `ja4`,
  `fp` (JA4 + H2-fp), `host`, `header:<name>` (API-ключ), `cookie:<name>`
  (сессия). Если части ключа у запроса нет, лимит к нему не применяется.
  Позже: `asn`, `session` (токен `__bs`, M4).
- Фильтры лимита: `hosts`, `paths` (glob), `methods`, `classes` — так лимит
  зависит от класса (отдельные записи для `human` / `suspicious` / `bot`).
- Каждый подходящий лимит учитывает запрос; отказ первого — ответ 429 с
  `Retry-After`, `RateLimit-Policy: "<name>";q=<burst>;w=<окно>` и
  `RateLimit: "<name>";r=0;t=<сек>` (черновик IETF). В shadow-режиме хоста
  запрос проходит, в событии `would_action: rate_limit`. Правило `allow`
  (мониторинг, партнёры) обходит лимиты.

```yaml
rate_limits:
  - name: login
    paths: [/login]
    methods: [POST]
    key: [ip]
    rate: 5/m
  - name: bots
    classes: [bot]
    key: [ip_prefix]
    rate: 30/m
  - name: api
    paths: ["/api/*"]
    key: ["header:x-api-key"]
    rate: 100/s
    burst: 200
```

### 8.2. Режимы

| Режим        | Как работает                                                        | Когда                         |
|--------------|---------------------------------------------------------------------|-------------------------------|
| `local`      | общее для всех воркеров хранилище в памяти, 64 шарда с блокировками ✅ | один узел, всё по умолчанию   |
| `synced`     | локально + каждые 100–250 мс дельты в Valkey и чтение глобального значения | несколько узлов, погрешность ±5–10 % допустима |
| `strict`     | атомарный GCRA в Valkey (Lua) синхронно на запрос                   | логин, оплата, регистрация    |

Если Valkey недоступен, `synced` и `strict` деградируют до `local`, а не
отказывают в обслуживании.

### 8.3. Защита самого шлюза

- `connection_limits` ✅: число открытых соединений с IP (`open_per_ip`) и
  скорость новых (`new_per_ip`, `new_burst_per_ip`) — проверяются сразу
  после `accept`, до TLS (самой дорогой части). По умолчанию выключены:
  за общим NAT много честных клиентов делят один IP.
- `pending_per_ip` ✅ (по умолчанию 128): соединения с IP, которые ещё не
  дошли до заголовков первого запроса (ClientHello, хендшейк, заголовки).
- Таймауты ✅: ClientHello 5 с, хендшейк 10 с, заголовки запроса 10 с
  (`timeouts.request_headers`), idle 300 с. Минимальная скорость тела —
  позже.
- Лимиты H2 ✅: `MAX_CONCURRENT_STREAMS` 100, rapid reset, CONTINUATION,
  SETTINGS/PING flood; `max_requests_per_connection` для HTTP/1.1 и HTTP/2.
- `/__bs/*` ✅ — свой лимит по IP (`challenge.endpoint_rate`).

Подробности и что шлюз не защищает — раздел 11.1.

## 9. Политики и конфигурация

### 9.1. Источники

1. `bot-shield.yaml` — глобальные настройки, режимы, пороги, правила,
   лимиты.
2. Docker-лейблы `botshield.*` на контейнерах — режим, passthrough и лимиты
   для хостов контейнера ✅.
3. `admin/api` — оперативные allow/deny с TTL (M3, дальше).

Приоритет режима хоста: `policy.hosts` из YAML (точное имя, затем
`*.parent`) → лейблы → глобальный `mode`. Явная запись в YAML всегда
главнее: так можно зафиксировать хост, не трогая контейнер. Лимиты из
лейблов действуют вместе с лимитами из YAML. Лейблы собираются в
неизменяемый снапшот, который атомарно подменяется (как сертификаты).

### 9.2. Привязка лейблов к хостам

Хосты контейнера определяются так:

1. `botshield.hosts=a.example.com,b.example.com`, если задан явно;
2. иначе разбором `Host(...)` (с любыми кавычками, несколько хостов и
   `||`) из всех `traefik.http.routers.*.rule` того же контейнера.

Контейнеры без лейблов `botshield.*` не затрагиваются. Если два контейнера
претендуют на один хост, побеждает первый по имени, остальные получают
предупреждение в логе. Ошибочный лейбл пропускается с предупреждением и не
влияет на остальные.

Шлюз опрашивает `GET /containers/json` через unix-сокет Docker
(`docker.socket`, по умолчанию выключено; `docker.poll_interval`, 5 с) и
пересобирает политики только при изменении ответа. Если Docker недоступен,
остаются последние известные политики.

### 9.3. Схема лейблов

```yaml
labels:
  botshield.hosts: "shop.example.com,www.shop.example.com"  # опционально
  botshield.mode: enforce               # shadow | enforce | off
  botshield.passthrough: "false"        # true: не терминировать TLS
  # botshield.ratelimit.<имя>: rate=<n>/<s|m|h|d> [burst=<n>] [key=...]
  #                            [path=<glob,...>] [methods=...] [classes=...]
  botshield.ratelimit.api: "rate=20/s burst=40 key=ip,header:x-api-key path=/api/*"
  botshield.ratelimit.login: "rate=5/m key=ip path=/login methods=POST"
```

`off` — только проксирование: без скоринга, правил, лимитов и заголовков
`X-Bot-*` (события пишутся). Лимит из лейбла называется
`<контейнер>/<имя>` и действует только на хостах контейнера. Позже:
`challenge.paths`, `ai_crawlers`, `honeypot.paths` (M4–M5).

### 9.4. Фрагмент `bot-shield.yaml`

```yaml
listen:
  http: ":80"
  https: ":443"
traefik:
  acme_json: /traefik/acme.json
  upstream_https: 127.0.0.1:8443
  upstream_http: 127.0.0.1:8080
  docker_socket: /var/run/docker.sock
mode: shadow                            # глобально, хост может переопределить
policies:
  default:
    thresholds: { suspicious: 30, bot: 70 }
    actions:   { suspicious: challenge, bot: block }
    ratelimit:
      - { key: fp, rate: 120/m, burst: 60, class: [human] }
      - { key: ip_prefix, rate: 30/m, class: [suspicious] }
  api:
    actions: { suspicious: throttle, bot: block }   # без интерстишиала
rules:
  - name: datacenter-no-token
    expr: 'net.asn_type == "datacenter" && !token.valid && score >= 20'
    action: challenge
lists:
  known_scrapers: file:///etc/bot-shield/lists/scrapers.txt
challenge:
  keys_file: /etc/bot-shield/keys.json  # пусто = случайный ключ на запуск
  token_ttl: 12h
  difficulty: { suspicious: 16, bot: 19 }
  token_credit: 40
storage:
  valkey: ""                            # пусто = только локальное состояние
events:
  nats: nats://127.0.0.1:4222
  sample_allow: 0.05                    # allow сэмплируются, остальное — 100 %
```

## 10. Данные, аналитика, приватность

### 10.1. События

Два типа, JSON в NATS (`<prefix>.conn`, `<prefix>.req`), схема ClickHouse —
`deploy/clickhouse/schema.sql`:

- **conn** — при закрытии соединения: `ts_ms, instance, conn_id, listener,
  ip_prefix, ip_hash, route, reason, duration_ms, bytes_in, bytes_out,
  requests, sni, tls_version, alpn_offered, alpn, ja4, ja4_r, tcp_fp, ja4t,
  h2_fp`. Отправляется для всех маршрутов, включая reject.
- **req** — на каждый увиденный HTTP-запрос: `ts_ms, instance, conn_id, seq,
  ip_prefix, ip_hash, http_version, method, host, path_group, header_fp,
  header_names[], pseudo_order, has_cookie, has_referer, ja4h` + отпечатки
  соединения + `user_agent, accept*, sec_ch_ua*, sec_fetch_*`.

Пустые поля не передаются. С M2 добавятся `score, class, reasons[], action,
would_action`; с M3 — поля rate limit; ASN/страна — с IP-базами.

Сериализация — JSON (ADR-010): ClickHouse читает его NATS engine без
промежуточного сервиса. В ClickHouse события лежат в `MergeTree` с
партиционированием по дню, рядом — почасовая агрегация по отпечаткам
(`fp_hourly`) для кластеризации.

### 10.2. Хранение

| Данные                      | Срок        |
|-----------------------------|-------------|
| Сырые события               | 14 дней     |
| Агрегаты (час × хост × fp)  | 180 дней    |
| Библиотека отпечатков       | бессрочно, версионируется |

### 10.3. Приватность

- Полный IP в долговременное хранилище не пишется: только префикс и хеш с
  солью, которая ротируется.
- Сигналы JS-челленджа хешируются на клиенте, сырые значения canvas и WebGL не
  передаются.
- Query string не логируется, только `path_group` (нормализованный путь).
- Есть процедура удаления данных по запросу (по хешу IP или токену). Это
  требование GDPR и 152-ФЗ.

### 10.4. Петля улучшения

1. Кластеризация по (`ja4`, `h2_fp`, `header_fp`) в ClickHouse:
   `cluster_daily` (AggregatingMergeTree, заполняется materialized view из
   `req`, проверенные краулеры исключены) хранит по дням запросы, клиентов,
   хосты, долю запросов с сигналами `behavior_*`/`honeypot*`/`fake_crawler`,
   долю класса bot, попадания в honeypot, топ причин и первое появление.
   Параметризованное представление `cluster_candidates(days, min_requests,
   min_anomaly)` отбирает кластеры, которых библиотека ещё не знает (нет
   `known_automation:*`), с долей аномалий не ниже порога или с попаданиями
   в honeypot. `tools/cluster_candidates.py` печатает их таблицей или
   (`--yaml`) готовыми записями для `automation:` в
   `deploy/fingerprints.yaml` с предложенным весом (80 при ≥ 60 % аномалий,
   50 при ≥ 30 %, 30 — только honeypot: это может быть один клиент за общим
   NAT). Проверено на ClickHouse 25.8 с синтетическими событиями: браузеры,
   известная автоматизация и проверенный краулер отфильтрованы.
2. Кандидаты разбираются вручную через UI и `admin/api`, затем попадают в
   библиотеку отпечатков или в правила.
3. Обновление библиотеки — версионированный файл, который шлюз применяет
   горячей перезагрузкой.

## 11. Отказоустойчивость

- **Fail-open** (ADR-012). Два уровня:
  1. *Зависание воркера.* Каждый воркер раз в 500 мс отмечается в
     `Heartbeats` таймером на своём event loop. Если loop завис
     (блокирующий вызов, бесконечный цикл), отметки прекращаются, и через
     5 с `GET /health` на порту метрик отвечает 503 `worker N stalled`.
     Под systemd (`Type=notify`, `WatchdogSec=10`) шлюз шлёт `WATCHDOG=1`
     только пока все воркеры живы, и systemd убивает и перезапускает
     зависший процесс. `sd_notify` реализован сам, без libsystemd.
  2. *Шлюз не отвечает* (упал, перезапускается, завис весь процесс).
     `bot-shield-watchdog` раз в секунду опрашивает `/health`; после 3
     неудач подряд выполняет `--on-fail`
     (`nft -f failopen/failopen-on.nft`): новые соединения на :443/:80
     перенаправляются (`redirect`) в Traefik на :8443/:8080. После 5
     успешных проверок подряд — `--on-recover` (`failopen-off.nft`).
     Начальное состояние неизвестно, поэтому первое решение применяется
     всегда: редирект, оставшийся от упавшего watchdog, снимается.
     Неудачная команда повторяется на следующей проверке. Остановка
     watchdog редирект не трогает (доступность важнее защиты). Состояние —
     в textfile для node_exporter: `bot_shield_failopen_active`,
     `bot_shield_failopen_switches_total`.

  Traefik слушает :8443/:8080 на всех адресах, чтобы редирект работал и для
  IPv4, и для IPv6 (DNAT на loopback возможен только для IPv4). Снаружи эти
  порты закрывает таблица `inet bot_shield_failopen`
  (`failopen/bot-shield.nft`): пропускаются только loopback и соединения с
  `ct status dnat`, то есть перенаправленные. Таблицу нужно загружать при
  загрузке системы (`include` в `/etc/nftables.conf`); unit watchdog
  перезагружает её при старте (идемпотентно). Без неё Traefik доступен в
  обход шлюза. Уже открытые соединения при переключении сохраняют свой путь
  (NAT решается на первом пакете). Файлы: `deploy/failopen/`,
  `deploy/systemd/`, сервис `bot-shield-watchdog` в `docker-compose.yml`
  (нужен `NET_ADMIN`). Проверено в контейнере Linux: 8443 снаружи закрыт,
  :443 при fail-open отвечает Traefik, после recover снова закрыт.
- **Внутренние ошибки.** Исключение или таймаут в скоринге дают `allow` с
  `X-Bot-Reasons: internal_error` и метрику. Запрос не теряется.
- **Зависимости.** Недоступность Valkey, NATS или ClickHouse не влияет на
  обслуживание: лимиты становятся локальными, события сбрасываются с
  метрикой `events_dropped`.
- **Перезапуск без потерь.** Новая версия стартует с `SO_REUSEPORT`, старая
  перестаёт принимать соединения и дорабатывает текущие (graceful drain до 30 с).
- **Несколько узлов** (когда понадобится): два инстанса bot-shield + Traefik за
  keepalived/VRRP, состояние лимитов через Valkey, ключи токенов общие.

### 11.1. Защита самого шлюза под нагрузкой

Шлюз фильтрует ботов и HTTP-флуд (L7). Он сам — сетевой сервис на одном
хосте, поэтому у него есть пределы, и часть защиты лежит за его пределами.

**Что шлюз не защищает.** Объёмные атаки L3/L4 — UDP/ICMP-флуд,
амплификация (DNS, NTP, memcached), SYN-флуд на гигабиты, забивание канала —
до процесса не доходят или упираются в канал и ядро раньше него. Это задача
провайдера или scrubbing-сервиса (anycast-фильтрация, BGP-переключение на
чистку). Ниже — то, что можно сделать на самом хосте, чтобы шлюз пережил
атаку поменьше и не стал слабым местом.

**L4: обход проверок через passthrough** (проверено на Traefik v3.5).
Passthrough отдаёт Traefik TLS как есть, а Traefik выбирает роутер по
`Host`, а не по SNI. Без мер ниже `curl -k` с SNI неизвестного хоста или
passthrough-хоста и `Host: <защищённый>` получал ответ защищённого сайта:

| Запрос (SNI → Host)                | Traefik по умолчанию | С мерами        |
|------------------------------------|----------------------|-----------------|
| без SNI → `shop`                   | 200                  | шлюз: reject; Traefik: handshake failure |
| `unknown.test` → `shop`            | 200                  | Traefik: handshake failure (`sniStrict`) |
| `grpc` (passthrough) → `shop`      | 200                  | Traefik: 421 Misdirected Request |

Меры: `no_sni: reject` в шлюзе (по умолчанию); в Traefik
`tls.options.default.sniStrict: true` и отдельная одинаковая по содержанию
опция `passthrough` на роутерах passthrough-хостов
(`traefik.http.routers.<r>.tls.options=passthrough@file`) — при разных
TLS-опциях у SNI и `Host` Traefik отвечает 421. Порт 80 проксируется в
Traefik без проверок, поэтому на `web` остаётся только редирект на HTTPS
(ACME HTTP-01 обрабатывается раньше редиректа). Всё это — в
`deploy/traefik.yml` и `deploy/traefik-tls.yml`.

**Медленные клиенты (slowloris).** До первого запроса соединение держит
слот в `pending_per_ip` и ограничено тайм-аутами ClientHello, хендшейка и
`request_headers`; заголовки каждого следующего запроса — тоже
`request_headers` от первого байта (HTTP/1.1) или от начала блока
HEADERS/CONTINUATION (HTTP/2). Простаивать между запросами keep-alive
соединение может до `idle`. Метрики:
`request_header_timeouts_total`, `connections_rejected_total{reason="pending_per_ip"}`.

**HTTP/2.** nghttp2 1.69 с явно заданными лимитами: rapid reset
(CVE-2023-44487) — корзина на 200 RST_STREAM с пополнением 33/с, после неё
GOAWAY; не больше 8 CONTINUATION на блок заголовков (CVE-2024-27316);
1000 ожидающих SETTINGS/PING ACK; 32 параметра в SETTINGS; «glitch»-лимит
nghttp2 по умолчанию. `max_requests_per_connection` (1000) закрывает
соединение (HTTP/1.1 — `Connection: close`, HTTP/2 — GOAWAY), чтобы
атакующий снова проходил лимиты соединений. RST от клиентов видны в
`h2_client_resets_total`.

**Служебные пути.** `/__bs/challenge` и `/__bs/verify` отвечает сам шлюз,
поэтому `rate_limits` их не видят; у них свой лимит по IP
(`challenge.endpoint_rate`, 30/мин, burst 10).

**Режим «под атакой».** `POST /attack {"host": "<host>|*", "ttl": "1h"}`
в admin API включает челлендж для всех клиентов хоста без валидного токена
`__bs`, независимо от скора и даже на shadow-хостах; правила и списки
`allow` и проверенные краулеры проходят. `attack.auto_rps` включает режим
автоматически, если RPS хоста держится выше порога ~10 с, на
`attack.auto_duration`. Состояние — в памяти, на перезапуск не переживает.
Метрики: `attack_hosts`, `attack_auto_activations_total`,
`attack_challenges_total`.

**Хост: sysctl.** Рекомендуемые значения (`/etc/sysctl.d/90-bot-shield.conf`):

```ini
# SYN cookies при переполнении очереди SYN: соединения не теряются,
# очередь не забивается SYN-флудом.
net.ipv4.tcp_syncookies = 1
net.ipv4.tcp_max_syn_backlog = 65535
# Очередь accept; шлюз слушает с backlog 4096, ядро обрежет до somaxconn.
net.core.somaxconn = 65535
net.core.netdev_max_backlog = 65535
# Меньше повторов SYN-ACK — полуоткрытые соединения живут меньше.
net.ipv4.tcp_synack_retries = 2
# Быстрее освобождать ресурсы закрытых соединений.
net.ipv4.tcp_fin_timeout = 15
net.ipv4.ip_local_port_range = 1024 65535
# Таблица conntrack: если nftables хранит состояние, её переполнение
# роняет новые соединения.
net.netfilter.nf_conntrack_max = 1048576
fs.file-max = 2097152
```

Плюс `LimitNOFILE=1048576` для процесса (`max_connections` по умолчанию
100 000). При `tcp_syncookies` ядро не сохраняет опции SYN, поэтому
отпечаток TCP у соединений, принятых по cookie, может быть неполным.

**Хост: nftables.** Лимит новых соединений по IP в ядре дешевле, чем в
шлюзе (отбрасывается ещё SYN), и работает до `accept`. Пороги — с запасом
на NAT:

```nft
table inet bot_shield {
  set flood {
    type ipv4_addr; flags dynamic, timeout; timeout 1m; size 262144;
  }
  set flood6 {
    type ipv6_addr; flags dynamic, timeout; timeout 1m; size 262144;
  }
  chain input {
    type filter hook input priority filter; policy accept;
    tcp dport { 80, 443 } ct state new \
      add @flood { ip saddr limit rate over 50/second burst 200 packets } drop
    tcp dport { 80, 443 } ct state new \
      add @flood6 { ip6 saddr and ffff:ffff:ffff:ffff:: limit rate over 50/second burst 200 packets } drop
    # Одновременных соединений с адреса.
    tcp dport { 80, 443 } ct state new meter conns { ip saddr ct count over 512 } drop
  }
}
```

IPv6 ограничивается по /64: у одного клиента обычно вся подсеть. Эти
правила дополняют `connection_limits` шлюза, а не заменяют: шлюз видит
TLS и HTTP и может быть точнее.

**План: XDP-фильтр (будущий ADR-016).** Когда SYN-флуд или поток мусорных
пакетов начнёт упираться в CPU ядра раньше, чем в канал, — фильтр XDP на
сетевом интерфейсе до стека TCP:

- блок-листы (CIDR) из admin API и автоматических решений шлюза — в
  eBPF-map, которую шлюз обновляет сам;
- SYN-cookie в XDP (`bpf_tcp_raw_gen_syncookie_ipv4`, ядро ≥ 6.0 —
  проверить на целевом) и лимит SYN по префиксу;
- сброс пакетов на :443/:80, которые не TCP, и фрагментов;
- fail-open: программа снимается, если шлюз не обновлял map дольше N
  секунд, — как watchdog из ADR-012.

Открытые вопросы для ADR: драйверы сетевой карты с native XDP на целевом
хосте (иначе generic XDP почти не выигрывает у nftables), загрузчик
(libbpf в процессе шлюза или отдельный сервис с `CAP_BPF`), как сохранить
сырой SYN для отпечатка TCP при SYN-cookie в XDP.

## 12. Наблюдаемость и эксплуатация

- **Метрики** (Prometheus, `:9900` на loopback): RPS по хосту и действию,
  распределение скоров, причины, латентность по стадиям (handshake, signals,
  score, upstream), хендшейки в секунду, срабатывания лимитов, состояние
  `acme.json`, возраст снапшота конфигурации, потерянные события.
- **Логи**: структурированный JSON, по умолчанию только не-`allow`.
- **Admin API** ✅ (`admin.socket`, unix-сокет с правами 0600, без TCP;
  выключен по умолчанию), JSON:

  | Запрос                         | Что делает                                                     |
  |--------------------------------|----------------------------------------------------------------|
  | `GET /status`                  | версия, uptime, режим, сертификаты, хосты из лейблов, соединения, ключи лимитов, NATS |
  | `GET /policy?host=<host>`      | итоговый режим и его источник (`policy.hosts` / `labels` / `mode`), маршрут, лимиты хоста |
  | `GET /lists`, `POST /lists`    | оперативные allow/block: `kind` (`ip` — адрес или CIDR, `ja4`, `header_fp` — glob), `action`, `host`, `ttl`, `comment` |
  | `DELETE /lists/<id>`           | удалить запись                                                 |
  | `GET /decisions?limit=&host=&class=` | последние решения (кольцевой буфер `admin.decisions`, в памяти) |
  | `GET /decisions/<request_id>`  | одно решение: сигналы, правила, действие, статус, длительность |
  | `GET /attack`, `POST /attack`, `DELETE /attack/<host>` | режим «под атакой»: `host` (имя, `*.parent` или `*` — все), `ttl`; раздел 11.1 |

  Записи списков главнее правил и класса (allow побеждает block, allow
  обходит лимиты), совпадение видно в причинах как `list:<id>`; с
  `admin.state_file` списки переживают перезапуск. Каждый запрос получает
  `request_id` (`<instance>-<соединение>-<номер>`), который уходит в Traefik
  заголовком `X-Bot-Request-Id` и попадает в события — по нему приложение
  ссылается на решение. Журнал решений хранит полный IP (он локальный и
  нужен, чтобы действовать), события — нет.

  ```bash
  curl --unix-socket /run/bot-shield/admin.sock http://bot-shield/policy?host=shop.example.com
  curl --unix-socket /run/bot-shield/admin.sock -d '{"kind":"ip","value":"203.0.113.0/24","action":"block","ttl":"1h"}' http://bot-shield/lists
  ```
- **Деплой**: docker-compose рядом с Traefik (`network_mode: host`, монтируются
  `acme.json` read-only и `docker.sock` read-only).
- **Безопасность шлюза**: процесс без root (`CAP_NET_BIND_SERVICE`), ключи
  токенов — в файле с правами 0600, `admin/api` — только unix-сокет, разбор
  ClientHello, H1 и H2 покрыт фаззингом (libFuzzer) в CI.

## 13. Миграция с «чистого» Traefik

1. Развернуть NATS и ClickHouse (опционально, но для калибровки желательно).
2. Запустить bot-shield на временных портах (`:10443`) в `mode: shadow` и
   проверить вручную: сертификаты подхватываются, хосты из лейблов определены,
   WebSocket работает.
3. В Traefik включить `proxyProtocol.trustedIPs` и перенести entrypoint'ы на
   loopback (`deploy/traefik.yml`); bot-shield перевести на :80/:443. Это делается одним
   перезапуском, простой — секунды.
4. Включить watchdog и fail-open.
5. Одна–две недели в shadow mode: разбирать `would_action`, калибровать пороги
   и профили, собирать allowlist (мониторинг, партнёры).
6. Включать `enforce` по одному хосту, начиная с самых скрепящихся.
7. gRPC проходит через шлюз (проверено, ADR-015). Хосты со специфичными
   протоколами поверх TLS (не HTTP) — в `passthrough_hosts` или лейбл
   `botshield.passthrough=true`.

- `fp/foxio/` — JA4T и JA4H за опцией `BOT_SHIELD_FOXIO` (ADR-014).
- `events/` — JSON-события `conn` и `req`, IP только префиксом и HMAC-хешем,
  путь без query с нормализацией (`/items/:n`), замена невалидного UTF-8.
- `events/nats_publisher` — свой NATS-клиент: отдельный поток, ограниченная
  очередь с отбрасыванием, пакетная запись, PING/PONG, переподключение с
  backoff; метрики `events_total`, `nats_connected`, `nats_reconnects`.
- `deploy/clickhouse/schema.sql` — NATS engine → MergeTree (14 дней) и
  `fp_hourly` (180 дней); проверено на ClickHouse 25.8 + NATS 2.11.
- Тесты: 70 юнит-тестов, e2e с фейковым NATS (события HTTP/1.1, HTTP/2,
  plain HTTP, passthrough, reject; нет query и полных IP).


### Статус M2 (часть 1: прокси)

Сделано (`src/proxy/`):

- `h2_server` — HTTP/2 к клиенту на nghttp2; Akamai-отпечаток строится из
  тех же кадров (`fp/h2_fingerprint`), отдельная пассивная прослушка больше
  не нужна.
- `h1_server` — HTTP/1.x к клиенту на llhttp: keep-alive, pipelining по
  очереди, потоковые тела (Content-Length и chunked), `100-continue`,
  ответы с Content-Length / chunked (+ трейлеры) / до закрытия для 1.0,
  лимит заголовков 64 КБ (431), дедлайн на заголовки (сейчас
  `timeouts.request_headers`, 10 с).
- WebSocket и другие Upgrade — отдельное HTTP/1.1-соединение к Traefik,
  после `101` — прозрачная пересылка.
- `h2_upstream` + `upstream_pool` — пул HTTP/2 к Traefik на воркер, ключ —
  SNI клиента, до `traefik.pool_size` соединений, очередь на время
  установки, idle-закрытие, корректный drain при остановке.
- `exchange` — пара запрос/ответ между сторонами; ручное управление
  окнами HTTP/2 (`consume` после фактической передачи), поэтому медленная
  сторона притормаживает быструю, а буферы ограничены.
- Заголовки: вырезаются hop-by-hop, `X-Forwarded-*`, `X-Real-IP`,
  `Forwarded`, `X-Bot-*` от клиента; выставляются свои `X-Forwarded-For`,
  `X-Real-IP`, `X-Forwarded-Proto/Host/Port`.
- Ответы шлюза: `502` при недоступном Traefik, `405` на CONNECT, `400/431`
  на битые запросы — с пометкой `local` в событиях.
- События `req` теперь отправляются по завершении и содержат `status`,
  `duration_ms`, `response_bytes`, `local`.
- Тесты: юнит-тесты сообщений и Exchange; e2e против собственного
  HTTP/2-апстрима (`tests/e2e/fake_upstream.cc`) — загрузки/выгрузки
  3–8 МБ, pipelining, трейлеры, WebSocket, 502, 50 параллельных запросов;
  ручная проверка с Traefik v3.5 + whoami (HTTP/1.1, HTTP/2, WebSocket,
  passthrough с PROXY, реальный IP).

Ограничения: HTTP/2 extended CONNECT (WebSocket поверх HTTP/2) не
объявляется — браузеры открывают для WebSocket отдельное HTTP/1.1-соединение;
серверный push не поддерживается (Traefik его не использует).


### Статус M2 (часть 2: вердикты)

Сделано:

- `fp/user_agent` — что заявляет User-Agent: семейство, движок
  (`chromium` / `firefox` / `webkit`; любой браузер на iOS — `webkit`),
  версия, ОС, инструменты (curl, python-requests, Go и т. д.), headless,
  заявленный краулер.
- `fp/library` — библиотека отпечатков в YAML (`deploy/fingerprints.yaml`,

  движков (хеш шифров JA4, порядок псевдозаголовков HTTP/2, с какой версии
  Client Hints и Sec-Fetch-*), сигнатуры автоматизации с glob-шаблонами,
  веса сигналов. Хеши шифров пересчитаны из списков cipher suites браузеров
  и совпали с опубликованными (`8daaf6152771`, `5b57614c22b0`,
  `a09f3c656075`).
- `score/scorer` — сигналы: `empty_user_agent`, `automation_user_agent`,
  `headless_user_agent`, `unverified_crawler`, `ua_tls_mismatch`,
  `ua_h2_mismatch`, `browser_without_h2`, `missing_client_hints`,
  `missing_fetch_metadata`, `missing_accept_language`, `os_tcp_mismatch`,

- `score/policy` — `mode: shadow|enforce` глобально и `policy.hosts` для

- Каждый запрос получает в Traefik `X-Bot-Score`, `X-Bot-Class`,

- `score/rules` — правила на своём языке условий (ADR-008): `allow`,

Не сделано: throttle и challenge (M3/M4), горячая перезагрузка библиотеки

## 15. ADR

Формат: контекст → решение → альтернативы → последствия.

### ADR-001. TLS-фронт перед Traefik

- **Статус:** принято.
- **Контекст.** Много сайтов уже работают за Traefik (docker-лейблы, ACME).
  Основной метод — отпечатки TCP, TLS и HTTP/2, для которых нужны сырой SYN,
  ClientHello и кадры H2. Их видит только тот, кто первым принимает
  соединение и терминирует TLS.
- **Решение.** bot-shield слушает :80/:443, терминирует TLS и проксирует в
  Traefik, который переезжает на loopback.
- **Альтернативы.**
  - *ForwardAuth в Traefik*: тривиально встраивается, но шлюз не видит TLS,
    H2 и TCP, а заголовки приходят переупорядоченными и канонизированными.
    Основной метод теряется. Оставлен как возможный «лёгкий» режим.
  - *Плагин Traefik (Yaegi)*: нет доступа к сырому ClientHello и кадрам H2.
  - *L4-прослушка перед Traefik + ForwardAuth*: ForwardAuth не передаёт порт
    источника, поэтому соединение невозможно надёжно сопоставить с запросом
    (особенно за NAT). Нет H2-отпечатков.
  - *Заменить Traefik*: теряются docker-провайдер и лейблы, миграция всех
    сайтов.
- **Последствия.** Полный набор сигналов. Шлюз становится критическим звеном,
  поэтому нужен fail-open (ADR-012). Появляются двойной TLS (ADR-004) и
  зависимость от формата `acme.json` (ADR-003).

### ADR-002. Data plane на C++20, thread-per-core

- **Статус:** принято.
- **Контекст.** Горячий путь: TLS, разбор H1/H2, скоринг; цель — ≤ 2 мс p99 и
  десятки тысяч RPS. Нужен низкоуровневый доступ к ClientHello, сокетным
  опциям и кадрам H2.
- **Решение.** C++20 (Google C++ Style, clang-format). Asio (standalone) с
  корутинами C++20, по воркеру на ядро с `SO_REUSEPORT`, без общего
  изменяемого состояния. Библиотеки: BoringSSL, llhttp, nghttp2, cel-cpp,
  ONNX Runtime (позже), hiredis/redis-plus-plus для Valkey, nats.c.
  ClientHello разбирается собственным парсером до передачи в BoringSSL через
  memory BIO (нужен в любом случае для L4-классификации).
- **Альтернативы.**
  - *Rust (Pingora)*: безопасность памяти, но к сырому ClientHello и кадрам
    H2 пришлось бы пробиваться через абстракции. Выбор в пользу C++ сделан по
    предпочтению автора.
  - *Go*: GC-паузы и необходимость форкать `crypto/tls` и `x/net/http2`.
  - *Seastar*: мощно, но тяжёлая зависимость и своя экосистема. Можно
    вернуться к нему, если Asio упрётся в производительность.
  - *io_uring напрямую*: возможная оптимизация позже, за абстракцией
    транспорта.
- **Последствия.** Высокая производительность и контроль. Риск ошибок памяти
  в парсерах снижается фаззингом, ASan и UBSan в CI и минимальной
  поверхностью собственного парсинга.

### ADR-003. Сертификаты читаются из `acme.json` Traefik

- **Статус:** принято.
- **Контекст.** Traefik уже выпускает и продлевает сертификаты для всех
  сайтов. Дублировать ACME — значит рисковать лимитами Let's Encrypt и
  гонками.
- **Решение.** bot-shield монтирует `acme.json` только для чтения, следит за
  ним через inotify и атомарно подменяет хранилище сертификатов. Челленджи
  ACME (HTTP-01 и TLS-ALPN-01) пробрасываются в Traefik. SNI без сертификата
  уходит в passthrough.
- **Альтернативы.**
  - *Свой ACME в bot-shield*: независимость от Traefik, но дублирование и
    конфликт за HTTP-01.
  - *Сертификаты через файловый провайдер*: потребовал бы перестройки
    существующей схемы.
- **Последствия.** Нулевая настройка сертификатов. Зависимость от формата
  `acme.json` (стабилен много лет; покрывается тестами на фикстурах разных
  версий Traefik). Сертификаты из других провайдеров Traefik (file provider)
  подключаются отдельным источником — каталогом PEM.

### ADR-004. Повторное шифрование до Traefik вместо plain HTTP

- **Статус:** принято.
- **Контекст.** Роутеры висят на `websecure` с `tls=true`. Перевод на
  plain-HTTP entrypoint потребовал бы правок лейблов на всех контейнерах.
- **Решение.** Upstream в Traefik — TLS на loopback с тем же SNI и `Host`, пул
  keep-alive соединений (новых хендшейков почти нет). HTTP/1.1 на старте
  (включая WebSocket upgrade), HTTP/2 — на этапе M6.
- **Альтернативы.** *Отдельный plain entrypoint `shielded`* — дешевле по CPU,
  но требует правок лейблов. Остаётся оптимизацией на будущее.
- **Последствия.** Немного больше CPU: симметричное шифрование на
  переиспользуемых соединениях — единицы процентов. gRPC до появления H2
  upstream идёт через `policy=passthrough`.

### ADR-005. Local-first rate limiting на GCRA

- **Статус:** принято.
- **Контекст.** Синхронный поход в Redis на каждый запрос добавляет задержку
  и делает лимиты точкой отказа. Точный глобальный лимит нужен лишь на
  немногих маршрутах.
- **Решение.** GCRA в памяти по умолчанию, режим `synced` с
  периодической синхронизацией дельт и режим `strict` с атомарным Lua в
  Valkey только для явно помеченных маршрутов. При отказе Valkey всё
  деградирует до `local`. Состояние `local` общее для всех воркеров
  процесса (64 шарда с мьютексами): соединения одного клиента ядро
  раскидывает по воркерам (`SO_REUSEPORT`), и раздельное состояние
  умножало бы лимит на число воркеров. Ключи с истёкшим состоянием
  вычищаются по ходу; выше лимита ключей новые не отслеживаются (fail open
  с метрикой).
- **Альтернативы.** *Только централизованный счётчик* — проще и точнее, но
  медленнее и хрупче. *Token bucket* — эквивалентен по возможностям, но
  хранит два значения на ключ вместо одного.
- **Последствия.** Погрешность ±5–10 % на нескольких узлах в `synced`, что
  приемлемо для антибота.

### ADR-006. Self-hosted, один владелец

- **Статус:** принято.
- **Контекст.** Шлюз защищает собственные сайты владельца.
- **Решение.** Нет тенантов, квот и изоляции. Единый конфиг, единый набор
  ключей. Хост — основная единица политики.
- **Альтернативы.** *Multi-tenant* — отвергнут как преждевременный.
- **Последствия.** Модель данных и конфиг сильно проще. Если понадобится
  мультитенантность, ключом будет `tenant_id` поверх `host`, без переделки
  горячего пути.

### ADR-007. Пассивные отпечатки + JS + PoW, stateless-токен

- **Статус:** принято.
- **Контекст.** Одни пассивные сигналы слабы против настоящих headless-
  браузеров. Капчи портят UX, сторонние сервисы добавляют внешнюю
  зависимость.
- **Решение.** Пассивные сигналы по умолчанию. Невидимый JS-челлендж с PoW
  при подозрении. Результат — HMAC-токен, привязанный к JA4 и подсети, без
  серверного состояния. Капча — плагином, выключена.
- **Альтернативы.** *Только пассивные* — дешевле, но слабее. *Серверные
  сессии в Valkey* — точный отзыв, но зависимость от хранилища в горячем пути.
  *Мобильный SDK* — позже.
- **Последствия.** API-клиенты не проходят интерстишиал, для них отдельная
  деградация (раздел 7.4). Скрипт челленджа нужно поддерживать в гонке с
  обходами: версионируется и обфусцируется при сборке. Отзыв отдельного
  токена без хранилища невозможен, только ротацией ключа; поэтому токен
  привязан к JA4 и подсети и живёт недолго.

### ADR-008. Правила на собственном языке условий

- **Статус:** принято (пересмотрено: изначально выбирался CEL).
- **Контекст.** Нужен язык правил, который безопасно выполнять в горячем
  пути: без циклов, с предсказуемой стоимостью, проверкой типов при загрузке.
  `cel-cpp` собирается только Bazel и тянет Abseil, protobuf и ANTLR — в
  CMake-сборку ложится плохо.
- **Решение.** Свой минимальный язык условий (`src/score/rules.cc`):
  литералы, поля запроса, `header()` / `has_header()` / `cidr()`,
  сравнения, glob, `in`, `and` / `or` / `not`. Компиляция в дерево при
  загрузке конфига с проверкой типов; вычисление — обход дерева без
  выделений памяти и с коротким замыканием, время линейно от размера
  условия. Действия правил: `allow`, `block`, `score`.
- **Альтернативы.** *CEL* — богаче и стандартнее, но тяжёлая зависимость.
  *Lua* — гибко, но тьюринг-полный язык в горячем пути, время выполнения
  приходится ограничивать счётчиком шагов.
- **Последствия.** Нет макросов, арифметики и пользовательских функций;
  расширяется добавлением полей и функций в `rules.cc`. Синтаксис
  совместим «в духе» CEL, переход на CEL позже возможен без смены модели
  `allow` / `block` / `score`.

### ADR-009. Valkey опционален, состояние в памяти по умолчанию

- **Статус:** принято.
- **Контекст.** На старте — один узел. Внешнее хранилище для одного узла даёт
  только новую точку отказа.
- **Решение.** Всё состояние в памяти. Valkey подключается при ≥ 2 узлах или
  для `strict` rate limit.
- **Альтернативы.** *Redis* — лицензионно менее удобен, протокол тот же.
  *Gossip между узлами* — сложнее, отложено.
- **Последствия.** После рестарта локальное состояние (окна, счётчики,
  deny-кеш) обнуляется. Это приемлемо: оно короткоживущее, а токены
  stateless.

### ADR-010. События: NATS JetStream → ClickHouse

- **Статус:** принято.
- **Контекст.** Аналитика и кластеризация требуют всех не-`allow` событий и
  сэмпла `allow`, а горячий путь не должен от этого зависеть.
- **Решение.** Неблокирующая отправка в NATS из отдельного потока с
  ограниченным буфером; при переполнении события сбрасываются с метрикой.
  Клиент свой, минимальный (core-протокол: CONNECT/PUB/PING/PONG), а не
  `nats.c`. События — JSON: ClickHouse читает их NATS engine напрямую.
  JetStream-поток на тех же subject'ах можно включить на сервере для
  буферизации и повторного чтения другими потребителями.
- **Альтернативы.** *Kafka* — избыточна для одного владельца. *Прямая вставка
  в ClickHouse* — нужна своя буферизация и ретраи в шлюзе.
- **Последствия.** Две дополнительные сущности в инфраструктуре; обе
  опциональны для работы шлюза. NATS engine ClickHouse подписан на core
  NATS: пока ClickHouse лежит, события теряются (это аналитика, не учёт).
  JSON больше бинарных форматов, но при текущих объёмах это не узкое место.

### ADR-011. HTTP/3 терминирует шлюз, а не Traefik

- **Статус:** принято (до M6 — «HTTP/3 отложен»).
- **Контекст.** Если Traefik анонсирует `Alt-Svc: h3`, браузеры уходят на
  QUIC (UDP/443) мимо TCP-фронта.
- **Решение.** HTTP/3 в Traefik выключен всегда. Шлюз всегда вырезает
  `Alt-Svc` из ответов Traefik. С M6 шлюз сам принимает QUIC на порту
  HTTPS (`http3.enabled`, по умолчанию выключено) и тогда анонсирует
  `Alt-Svc: h3=":443"; ma=86400` в ответах по TCP и HTTP/3:
  - QUIC — ngtcp2 1.25 с крипто-бэкендом BoringSSL, HTTP/3 — nghttp3 1.18
    (FetchContent, как остальные зависимости). Отдельный `SSL_CTX` под QUIC;
    сертификат выбирается по SNI в `select_certificate`-колбэке из того же
    `acme.json`.
  - Запросы HTTP/3 становятся теми же `Exchange` и идут в Traefik по
    HTTP/2-пулу; вердикты, правила, лимиты, челлендж, события — общие с
    TCP (`MakeQuicObserver` оборачивает тот же `ConnectionObserver`,
    listener `quic`).
  - Хост без сертификата или passthrough-хост получает отказ в handshake:
    клиент переходит на TCP, где работает passthrough.
  - Retry (`http3.retry`, по умолчанию включён): состояние соединения
    заводится только после проверки адреса токеном, поэтому флуд
    Initial-пакетами с поддельных адресов ничего не стоит (ценой одного RTT).
    Лимит соединений на воркер — `http3.max_connections`. Миграция
    соединений выключена (`disable_active_migration`): при `SO_REUSEPORT`
    ядро распределяет UDP по 4-tuple, и мигрировавший клиент попал бы на
    другой воркер.
  - Отпечатки: JA4 с префиксом `q` (из ClientHello внутри QUIC) и
    `quic_fp` — идентификаторы QUIC transport parameters в порядке клиента
    (без GREASE), в событии `conn`. Проверки, откалиброванные под TCP-стек
    браузера (шифры JA4 — в QUIC их только три TLS 1.3, порядок
    псевдозаголовков HTTP/2), для QUIC пропускаются, пока в библиотеке нет
    проверенных QUIC-профилей.
- **Альтернативы.** *quiche или msquic* — другие языки и TLS-стеки;
  ngtcp2/nghttp3 — те же авторы, что nghttp2, и тот же BoringSSL. *HTTP/3
  в Traefik* — QUIC шёл бы мимо отпечатков.
- **Последствия.** UDP/443 принадлежит шлюзу. Fail-open перенаправляет
  только TCP: при отказе шлюза клиенты HTTP/3 после тайм-аута переходят на
  TCP. Проверено e2e с curl (ngtcp2): GET, загрузка 2 МБ, скачивание 5 МБ,
  блок на enforce-хосте, Alt-Svc, отказ для хоста без сертификата; сборка
  под Linux с `SO_REUSEPORT` на UDP.

### ADR-012. Fail-open через watchdog и nftables

- **Статус:** принято.
- **Контекст.** bot-shield стоит перед всеми сайтами. Его отказ не должен
  означать их отказ.
- **Решение.** Отдельный watchdog проверяет здоровье шлюза и при отказе
  включает nftables-редирект :80/:443 → Traefik. Traefik слушает на всех
  адресах (:8443/:8080), постоянная nftables-таблица закрывает эти порты
  снаружи для всего, кроме перенаправленных соединений: так fail-open
  работает и для IPv6. Зависание отдельного воркера ловится heartbeat'ами и
  systemd watchdog. Внутренние ошибки скоринга превращаются в `allow`.
- **Альтернативы.** *Fail-closed* — неприемлемо для владельца сайтов.
  *Только `Restart=always`* — не защищает от зависания без падения.
  *DNAT на 127.0.0.1 с `route_localnet`* — Traefik остаётся на loopback, но
  только IPv4.
- **Последствия.** Во время отказа защиты нет, но сайты доступны. Переключение
  видно в метриках и алертах. Безопасность Traefik зависит от загруженной
  nftables-таблицы: без неё :8443/:8080 открыты наружу.


### ADR-013. M0: TLS-туннель до Traefik и PROXY protocol v2

- **Статус:** заменено ADR-015 (действовало на этапах M0–M1).
- **Контекст.** Для M0 нужно терминировать TLS и сохранить все возможности
  сайтов: HTTP/1.1, HTTP/2, WebSocket, длинные стримы. Полноценный HTTP-прокси
  (llhttp и nghttp2, перекодирование кадров, подстановка заголовков) нужен
  только к M2, когда появятся решения на уровне запроса.
- **Решение.** После хендшейка с клиентом шлюз открывает к Traefik отдельное
  TLS-соединение с тем же SNI, предлагает ровно тот ALPN, который выбрал
  клиент, и копирует расшифрованные байты в обе стороны. Реальный адрес
  клиента передаётся заголовком PROXY protocol v2 в начале каждого
  upstream-соединения. Если Traefik выбрал другой ALPN, соединение
  закрывается с метрикой `alpn_mismatches`.
- **Альтернативы.**
  - *Сразу HTTP-aware прокси* — больше кода до первых сигналов. Отложен до
    M2, где он действительно нужен.
  - *`forwardedHeaders` вместо PROXY* — требует вставки заголовков, то есть
    разбора HTTP. Невозможно в туннеле.
- **Последствия.** Одно upstream-соединение и один локальный TLS-хендшейк на
  каждое клиентское соединение, без переиспользования. На loopback это доли
  миллисекунды, но при большом числе коротких соединений — заметный CPU;
  уходит вместе с туннелем в M2. Заголовки `X-Bot-*` до M2 не передаются.


### ADR-014. Свои отпечатки TCP/HTTP, JA4T/JA4H — отдельным модулем

- **Статус:** принято.
- **Контекст.** JA4 (TLS) распространяется под BSD-3. JA4T и JA4H — под
  FoxIO License 1.1: бесплатно для защиты своих систем, но монетизация
  (продажа продукта или сервиса с ними) требует лицензии FoxIO. При этом
  они совместимы с внешними базами отпечатков.
- **Решение.** Основа скоринга и библиотеки — свои форматы без ограничений:
  `tcp_fp`, `header_fp` и открытый Akamai-формат `h2_fp`. JA4 считается
  всегда. JA4T и JA4H живут в `src/fp/foxio/` и собираются только с
  `-DBOT_SHIELD_FOXIO=ON` (по умолчанию включено, пока шлюз защищает свои
  сайты); они пишутся в события дополнительными полями.
- **Альтернативы.** *Только JA4+* — проще, но привязывает продукт к
  лицензии. *Только свои форматы* — теряется совместимость с внешними базами.
- **Последствия.** Сборка с `BOT_SHIELD_FOXIO=OFF` не содержит кода JA4+
  (проверено: 0 символов `foxio::` в бинарнике). Правила и библиотека
  отпечатков не должны зависеть от `ja4t`/`ja4h` как от единственного
  признака.


### ADR-015. Полный HTTP-прокси с пулом HTTP/2 к Traefik

- **Статус:** принято, заменяет ADR-013.
- **Контекст.** Для решений по запросам (скоринг, блок, челлендж, `X-Bot-*`)
  шлюз должен понимать HTTP и уметь отвечать сам. Туннель «соединение в
  соединение» этого не даёт, а TLS-хендшейк к Traefik на каждое клиентское
  соединение тратит CPU.
- **Решение.** Шлюз сам говорит HTTP/1.1 и HTTP/2 с клиентом и ходит в
  Traefik через пул HTTP/2-соединений на воркер (ключ — SNI, мультиплексирование
  потоков). Реальный адрес клиента — в `X-Forwarded-For` / `X-Real-IP`
  (Traefik доверяет им по `forwardedHeaders.trustedIPs`); те же заголовки
  от клиента вырезаются. Passthrough и порт 80 по-прежнему с PROXY v2.
  WebSocket — отдельным HTTP/1.1-соединением. Управление потоком сквозное:
  WINDOW_UPDATE отправляется только после того, как байты ушли дальше.
- **Альтернативы.**
  - *Переписывающий туннель* (1:1 соединения, правка заголовков в потоке,
    перекодирование HPACK) — меньше кода и без правки Traefik, но на HTTP/2
    свой ответ клиенту можно дать только сбросом потока, а вставка страницы
    челленджа конфликтует с flow control.
  - *Пул HTTP/1.1 keep-alive* — проще, но ломает gRPC (трейлеры) и требует
    больше соединений.
- **Последствия.** В Traefik добавляется `forwardedHeaders.trustedIPs` на
  `websecure`. Шлюз становится полноценным HTTP-прокси: корректность
  HTTP-семантики (тела, трейлеры, 1xx, keep-alive) теперь на нём и покрыта
  e2e. gRPC проверен на Traefik v3.5 с grpc-go за ним (h2c): reflection,
  unary, серверный, клиентский и двунаправленный стриминг, ошибки со
  статусом в трейлерах, сообщения 300 КБ. Проверка нашла ошибку: ответ
  «trailers-only» (один HEADERS с `grpc-status` и END_STREAM — так gRPC
  отвечает ошибкой без тела) шлюз делил на HEADERS и пустой DATA, и
  клиенты видели «stream closed without trailers». Теперь апстрим передаёт
  «ответ уже закончен» вместе с заголовками, e2e проверяет кадры. Для
  gRPC-хостов `passthrough_hosts` больше не нужен; правила и лимиты к ним
  применимы, но челлендж для gRPC-клиентов смысла не имеет (не браузер) —
  для них `allow`-правило или режим `off`.

## 16. Открытые вопросы


- Целевая нагрузка в цифрах (пиковый RPS, число хостов) — уточнить для
  нагрузочного теста M0.
- Источник IP-баз (ASN, датацентры, резидентные прокси): бесплатные
  (iptoasn, списки облаков) или коммерческие.
- Нужна ли инъекция `<script>` челленджа в HTML-ответы для невидимого сбора
  сигналов без интерстишиала. Требует разбора и переписывания тела ответа,
  стоит отдельно оценить.
- Мобильные приложения на тех же хостах: нужен ли SDK с App Attest и Play
  Integrity, или достаточно API-ключей и лимитов.
- Политика для AI-краулеров: блок, allow, или `402` с оплатой.
- Где запускать офлайн-задачи и UI: на том же хосте или отдельно.
