# bot-shield: архитектура

Статус: черновик v0.1 · 2026-10-17

bot-shield — self-hosted шлюз для фильтрации ботов, скрепинга и прочей
автоматизации. Основной метод — отпечатки клиента на уровнях TCP, TLS, HTTP и
JS и проверка их согласованности с тем, кем клиент себя заявляет. Шлюз также
отвечает за rate limiting. Встаёт перед существующим Traefik без изменений в
его конфигурации и лейблах контейнеров.

## 1. Цели и рамки

### Цели

- Отличать браузеры людей от автоматизации: HTTP-библиотек, headless-браузеров,
  impersonation-клиентов (`curl-impersonate`, `tls-client`), скреперов.
- Ограничивать частоту запросов по гибким ключам (IP, подсеть, ASN, отпечаток,
  сессия, API-ключ) с порогами, зависящими от скора.
- Встраиваться перед уже работающим Traefik **без правок лейблов и роутеров**.
- Пропускать «хороших» ботов (поисковики, мониторинг, партнёров) после проверки
  подлинности.
- Отдавать приложениям сигнал (`X-Bot-Score`), чтобы они могли принимать свои
  решения.
- Иметь shadow mode: наблюдать без вмешательства и калибровать пороги.

### Целевые нефункциональные параметры

| Параметр                         | Цель                                   |
|----------------------------------|----------------------------------------|
| Пропускная способность узла      | 20–50k RPS, 50–100k одновременных соед.|
| Добавочная задержка (p99)        | ≤ 2 мс на запрос без челленджа         |
| Новые TLS-хендшейки              | ≥ 5k/с на узел (ECDHE, 8 ядер)         |
| Доступность                      | fail-open: отказ шлюза ≠ отказ сайтов  |
| Применение изменений политик     | ≤ 5 с без перезапуска                  |

Цифры — ориентиры для проектирования, уточняются нагрузочными тестами.

### Не цели (на v1)

- Multi-tenant SaaS: один владелец, одна инсталляция (ADR-006).
- WAF (SQLi, XSS и т. п.) — отдельная задача.
- Защита от объёмного L3/L4 DDoS — это уровень провайдера или CDN. Шлюз
  защищает себя лимитами соединений, но не пропускную способность канала.
- Мобильный SDK с аттестацией устройства — возможное расширение (раздел 16).
- HTTP/3 (QUIC) на входе — отложено (ADR-011).

## 2. Топология и встраивание

```
                         ┌────────────────────────── хост ──────────────────────────┐
                         │                                                          │
 Internet ──► :80/:443 ──┤ bot-shield (network_mode: host)                          │
                         │   ├─ L4-классификатор (peek ClientHello)                 │
                         │   │    ├─ ALPN acme-tls/1 ────────────── L4 passthrough ─┼─┐
                         │   │    ├─ нет сертификата для SNI ────── L4 passthrough ─┼─┤
                         │   │    └─ host с policy=passthrough ─── L4 passthrough ─┼─┤
                         │   ├─ TLS-терминация (серты из acme.json)                 │ │
                         │   ├─ сигналы → скоринг → действие → rate limit           │ │
                         │   └─ upstream: HTTPS, тот же SNI/Host ───────────────────┼─┤
                         │                                                          │ ▼
                         │ Traefik 127.0.0.1:8443 / :8080  (роутинг, ACME, лейблы) ─┼──► сайты
                         │                                                          │
                         │ Valkey (опц.) · NATS · ClickHouse                        │
                         └──────────────────────────────────────────────────────────┘
```

Что меняется в Traefik:

1. `entryPoints.web` и `entryPoints.websecure` переезжают на `127.0.0.1:8080` и
   `127.0.0.1:8443` (или на внутренний адрес docker-сети).
2. В entrypoint'ах включаются `proxyProtocol.trustedIPs` и (на
   `websecure`) `forwardedHeaders.trustedIPs` с адресом bot-shield.
   Passthrough-соединения и порт 80 приходят с PROXY protocol v2.
   Терминированные запросы идут по пулу HTTP/2-соединений без PROXY и несут
   адрес клиента в `X-Forwarded-For` / `X-Real-IP`, которые шлюз выставляет
   сам, вырезая присланные клиентом (ADR-015). Traefik применяет PROXY,
   только если тот пришёл, поэтому оба вида соединений живут на одном
   entrypoint (проверено на Traefik v3.5). Пример — `deploy/traefik.yml`.
3. Сертификаты, ACME-резолверы, роутеры, middleware и лейблы остаются как есть.

Что делает bot-shield:

- Читает `acme.json` Traefik (read-only mount) и опрашивает его на изменения
  (по умолчанию раз в 2 с). Traefik продолжает выпускать и продлевать сертификаты (ADR-003).
- Пробрасывает трафик в Traefik повторно по TLS с тем же SNI, поэтому роутеры
  с `tls=true` на `websecure` работают без изменений (ADR-004).
- HTTP-01 на :80 проксирует в Traefik как есть. ClientHello с ALPN `acme-tls/1`
  (TLS-ALPN-01) отдаёт Traefik на уровне L4.
- Для SNI, которого нет в `acme.json`, делает L4 passthrough только с
  IP-лимитами. Новый сайт не сломается до появления сертификата, а после
  перечитывания `acme.json` сразу попадёт под защиту.
- Слушает docker socket (read-only), как и Traefik, и берёт политики из лейблов
  `botshield.*` (раздел 9).

## 3. Компоненты

### 3.1. Data plane (C++20, один процесс `bot-shield`)

Модель: thread-per-core, `SO_REUSEPORT` на каждый воркер, без разделяемого
изменяемого состояния в горячем пути. Каждый воркер владеет своими
соединениями, шардом rate limiter и локальными кешами. Межпоточный обмен идёт
через lock-free очереди и RCU-снапшоты конфигурации (ADR-002).

| Модуль                 | Ответственность                                                         |
|------------------------|-------------------------------------------------------------------------|
| `net/listener`         | accept, `TCP_SAVE_SYN`/`TCP_SAVED_SYN`, лимиты соединений на IP          |
| `net/l4_classifier`    | чтение и разбор ClientHello до TLS, выбор: терминировать или passthrough |
| `net/splice`           | L4 passthrough, PROXY protocol v2 (см. ниже); `splice(2)` — оптимизация на потом |
| `tls/terminator`       | BoringSSL, выбор сертификата по SNI, сессии/тикеты                       |
| `tls/cert_store`       | загрузка `acme.json`, опрос изменений, атомарная подмена снапшота        |
| `http/h1`              | llhttp, сохранение исходного порядка и регистра заголовков               |
| `http/h2`              | nghttp2, перехват SETTINGS / WINDOW_UPDATE / PRIORITY / порядка псевдозаголовков |
| `signals/*`            | сборщики сигналов: tcp, tls, h2, headers, reputation, behavior           |
| `fp/library`           | библиотека известных клиентов, проверки согласованности                 |
| `score/engine`         | взвешенные сигналы → скор + коды причин, затем правила CEL               |
| `action/*`             | allow, tag, throttle, challenge, tarpit, block, decoy                   |
| `challenge/*`          | выдача и проверка JS/PoW-челленджей, подпись и проверка токенов          |
| `ratelimit/*`          | локальный GCRA, синхронизация с Valkey, строгий режим                    |
| `proxy/*`              | HTTP-aware прокси: HTTP/1.1 и HTTP/2 к клиенту, пул HTTP/2 к Traefik (ADR-015) |
| `events/emitter`       | компактные события запросов → NATS (с сэмплированием)                    |
| `config/*`             | YAML + docker-лейблы → снапшот политик, валидация, hot reload            |
| `admin/api`            | HTTP API на unix-сокете: статус, политики, allow/deny-листы, разбор решений |

**Про реальный IP клиента.** Traefik видит все соединения от bot-shield,
поэтому шлюз начинает каждое upstream-соединение с заголовка PROXY protocol v2
(адрес и порт клиента плюс TLV `PP2_TYPE_AUTHORITY` с SNI). На entrypoint'ах
Traefik для этого включён `proxyProtocol.trustedIPs`. Отключается в конфиге
(`traefik.proxy_protocol: false`), но тогда Traefik видит только 127.0.0.1.

### 3.2. Control plane

Отдельного сервиса на v1 нет: политики живут в YAML и docker-лейблах, а
`admin/api` встроен в процесс. Веб-UI (просмотр решений, allow/deny, графики)
появится позже как отдельное приложение поверх `admin/api` и ClickHouse.

### 3.3. Analytics plane

- **NATS JetStream** — буфер событий, развязывающий горячий путь и хранилище.
- **ClickHouse** — сырые события и агрегаты. Ingest через NATS table engine
  или маленький консьюмер.
- **Офлайн-задачи** (Python, по расписанию): кластеризация новых отпечатков,
  поиск аномалий, предложения правил, обновление `fp/library`, обучение модели
  (ONNX).

### 3.4. Состояние

- **Valkey** — распределённые счётчики rate limit, общие deny-листы, отзыв
  токенов. **На одном узле не обязателен**: всё работает в памяти (ADR-009).
- Локально в памяти: LRU-кеши репутации, поведенческие окна, снапшот
  библиотеки отпечатков, снапшоты IP-баз (ASN, датацентры, Tor).

## 4. Путь запроса

```
accept ─► TCP_SAVED_SYN ─► peek ClientHello ─► классификация
                                                  │
              ┌───────────── passthrough ─────────┤
              ▼                                   ▼
        splice в Traefik                   TLS handshake (BoringSSL)
        (только IP-лимиты)                        │
                                                  ▼
                                      HTTP/1.1 или HTTP/2 разбор
                                                  │
                         ┌────────────────────────┤ на каждый запрос:
                         ▼                        ▼
               служебные пути /__bs/*     сбор сигналов (conn-уровень кешируется)
               (челлендж, верификация)            │
                                                  ▼
                                    проверка токена __bs (если есть)
                                                  │
                                                  ▼
                                      скоринг → правила CEL → действие
                                                  │
                                                  ▼
                                    rate limit (ключи и лимиты по классу)
                                                  │
                     ┌──────────┬────────┬────────┼────────┬──────────┐
                     ▼          ▼        ▼        ▼        ▼          ▼
                   block    challenge  tarpit   decoy   throttle   allow/tag
                                                                      │
                                                                      ▼
                                      upstream в Traefik + X-Bot-Score/Reasons
                                                  │
                                                  ▼
                                       ответ клиенту, событие → NATS
```

Принципы:

- Сигналы уровня соединения (TCP, TLS, H2 SETTINGS) считаются один раз на
  соединение и переиспользуются всеми запросами в нём.
- В горячем пути нет синхронного сетевого I/O. Исключение — строгий режим rate
  limit для явно помеченных маршрутов (раздел 8).
- Решение детерминировано для одного снапшота конфигурации и состояния.
  `admin/api` умеет объяснить его по `request_id`.

## 5. Сигналы и отпечатки

### 5.1. Пассивные сигналы

| Уровень   | Что собираем                                                                 | Отпечаток            |
|-----------|-------------------------------------------------------------------------------|----------------------|
| TCP/IP    | TTL (с нормализацией к 64/128/255), window, MSS, window scale, порядок опций, DF, ECN | свой `tcp_fp` (+ JA4T, ADR-014) |
| TLS       | версия, cipher suites, порядок расширений, GREASE, supported_groups, sig_algs, ALPN, key_share, ECH | JA4 (+ JA3 для совместимости) |
| HTTP/2    | SETTINGS (порядок и значения), WINDOW_UPDATE, PRIORITY/priority frames, порядок псевдозаголовков | H2-fp (формат Akamai) |
| HTTP/1.1  | порядок и регистр заголовков, `Connection`, `Accept-*`                        | свой `header_fp` (+ JA4H, ADR-014) |
| Заголовки | `User-Agent`, `sec-ch-ua*`, `sec-fetch-*`, `accept-language`, `accept-encoding` | согласованность      |
| Сеть      | ASN, тип (датацентр, хостинг, мобильный, резидентный), Tor, известные прокси  | репутация            |

Форматы (реализация в `src/fp/`):

- `tcp_fp` — `<ip>:<начальный TTL>:<window>:<mss>:<wscale>:<опции>:<флаги>`,
  опции буквами в порядке на проводе, например `4:64:64240:1460:7:MSTNW:df`.
- `ja4` / `ja4_r` — JA4 по спецификации FoxIO (BSD-3), сверен с эталоном
  `t13d1516h2_8daaf6152771_e5627efa2ab1`.
- `h2_fp` — формат Akamai: `SETTINGS|WINDOW_UPDATE|PRIORITY|псевдозаголовки`,
  например `1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p`.
- `header_fp` — `<версия>:<число заголовков>:<sha256 имён по порядку, 12>`;
  регистр имён на HTTP/1.x сохраняется.
- `ja4t`, `ja4h` — только при сборке с `BOT_SHIELD_FOXIO=ON` (ADR-014).

HTTP читается пассивно: копия потока клиент → Traefik идёт в разборщик
(llhttp для HTTP/1.x, свой разбор кадров + HPACK из nghttp2 для HTTP/2).
Разборщик ничего не меняет и при любой ошибке, апгрейде (WebSocket) или
превышении лимитов (64 КБ заголовков, 128 запросов) просто отключается.

TCP SYN берётся через `setsockopt(TCP_SAVE_SYN)` на слушающем сокете и
`getsockopt(TCP_SAVED_SYN)` после `accept`. Для этого нужен Linux, а
контейнер должен работать в `network_mode: host`: при DNAT через docker-bridge
TTL уменьшается и часть картины искажается.

### 5.2. Проверки согласованности (основной метод)

`fp/library` хранит профили клиентов:

```yaml
- id: chrome-desktop
  ua_match: { family: Chrome, major: ">=120" }
  platforms: [Windows, macOS, Linux]
  ja4: ["t13d1516h2_8daaf6152771_*"]        # шаблоны
  h2: ["1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p"]
  header_order_h2: [":method", ":authority", ":scheme", ":path"]
  required_headers: [sec-ch-ua, sec-fetch-site, sec-fetch-mode, accept-language]
```

Проверки (каждая даёт код причины и вес):

- `ua_tls_mismatch`: UA говорит Chrome, а JA4 не из профиля Chrome.
- `ua_h2_mismatch`: H2 SETTINGS или порядок псевдозаголовков не совпадают с
  профилем.
- `os_tcp_mismatch`: UA говорит Windows, а TCP-стек похож на Linux.
- `missing_client_hints`: Chromium без `sec-ch-ua` на навигации.
- `fetch_meta_inconsistent`: `sec-fetch-mode=navigate`, но `accept` не HTML.
- `known_automation_fp`: JA4 или H2 из списка известных библиотек (Go
  `net/http`, Python `requests`/`httpx`/`aiohttp`, Node `undici` и т. д.).
- `impersonation_artifacts`: идеальный JA4 Chrome при нетипичном
  WINDOW_UPDATE или порядке заголовков (типично для `curl-impersonate`).

Нормальные расхождения (корпоративные TLS-прокси, антивирусы с MITM, старые
версии) снижают вес до «подозрительно», не до «бот». Для этого в библиотеке
есть профили `mitm-proxy-*`.

### 5.3. Активные сигналы (JS-челлендж)

Собирает скрипт челленджа (раздел 7):

- `navigator.*`: `webdriver`, `plugins`, `languages`, `hardwareConcurrency`,
  `deviceMemory`, `userAgentData` (сверка с заголовками).
- Отпечатки canvas, WebGL (vendor и renderer), audio, список шрифтов, метрики
  экрана. Каждый хешируется на клиенте и отправляется хешем.
- Маркеры автоматизации: следы CDP (`Runtime.enable`-побочки), Playwright,
  Puppeteer, `chrome.runtime` в headless, расхождение между main thread и
  Worker (`navigator` в Worker vs в окне).
- Тайминги: время выполнения PoW против заявленного `hardwareConcurrency`,
  джиттер `performance.now()`.

### 5.4. Поведенческие сигналы

Скользящие окна в памяти воркера (ключ — отпечаток + /24 или сессия):

- RPS и его регулярность (низкая дисперсия интервалов означает автоматизацию);
- энтропия путей, доля 404, обход пагинации, последовательный перебор ID;
- «API без страницы»: запросы к `/api/*` без предшествующей навигации;
- отсутствие запросов к статике у HTML-клиента (только для хостов, где статика
  идёт через шлюз);
- honeypot: обращение к ловушкам (раздел 6.3).

### 5.5. Хорошие боты

- Поисковики: reverse DNS → forward DNS (Googlebot, Bingbot, YandexBot и др.),
  результат кешируется по IP на 24 ч, плюс опубликованные IP-диапазоны.
- Web Bot Auth (HTTP Message Signatures): проверка подписи по каталогу ключей
  бота.
- Свой мониторинг и партнёры: allowlist по IP/CIDR, mTLS или API-ключу.
- Результат — класс `verified_bot` с отдельной политикой: можно разрешить
  индексацию, но запретить AI-краулерам (раздел 9).

## 6. Скоринг и действия

### 6.1. Скоринг

1. Каждый сработавший сигнал добавляет вес и код причины.
   `score = clamp(Σ w_i, 0, 100)`.
2. Валидный токен челленджа понижает скор на величину, зависящую от его
   класса, но не обнуляет поведенческие сигналы.
3. Правила CEL выполняются после скоринга и могут переопределить действие
   (ADR-008):

   ```cel
   request.path.startsWith("/api/") && fp.ja4 in lists.known_scrapers
     => block("scraper_list")
   score > 60 && net.asn_type == "datacenter" => challenge("pow")
   ```

4. Опционально (позже) ONNX-модель даёт дополнительный сигнал с весом.
   Модель советует, а не решает.

Классы: `human` (< 30), `suspicious` (30–69), `bot` (≥ 70), отдельно
`verified_bot`. Пороги задаются на политику.

### 6.2. Действия

| Действие    | Поведение                                                                       |
|-------------|----------------------------------------------------------------------------------|
| `allow`     | проксировать, добавить `X-Bot-Score`, `X-Bot-Class`, `X-Bot-Reasons`             |
| `tag`       | как `allow`, но явно для shadow mode (решение пишется в событие как «would_X»)   |
| `throttle`  | применить пониженный лимит класса                                                |
| `challenge` | навигация (`Accept: text/html`, GET) → страница челленджа; иначе 429 + JSON с `challenge_url` |
| `tarpit`    | медленная отдача (байт в N мс) с ограничением числа одновременных tarpit-соединений |
| `block`     | 403 (или 404 по политике), короткий ответ, отпечаток → кратковременный deny-кеш  |
| `decoy`     | отдать ловушечные или «отравленные» данные из шаблонов политики (опционально)    |

### 6.3. Honeypot и водяные знаки

- Пути-ловушки из политики (`/wp-admin/` на не-WordPress, невидимые ссылки при
  инжекте). Обращение к ним мгновенно ставит отпечатку и /24 высокий скор на
  TTL.
- Водяные знаки для `decoy`: уникальные токены в отравленных данных, чтобы
  потом находить, кто их унёс.

## 7. Челленджи и токен

### 7.1. Виды

- **Невидимый JS** — сбор сигналов из 5.3 и подписанный ответ. Проходит за
  < 300 мс.
- **PoW** — hashcash на SHA-256 через WebCrypto. Сложность зависит от скора:
  ~50 мс для «подозрительно», ~2 с для «скорее бот». Применяется вместе с JS.
- **Капча** — интерфейс плагина для стороннего провайдера, по умолчанию
  выключена.

### 7.2. Поток

```
GET /page  ──► challenge ──► 403 + HTML/JS (no-store), nonce, сложность
                                   │
     браузер: сбор сигналов + PoW  │
                                   ▼
POST /__bs/verify {nonce, pow, signals} ──► проверка ──► Set-Cookie: __bs=<token>
                                                          302 → исходный URL
```

Служебный префикс `/__bs/` резервируется на всех защищённых хостах (имя
настраивается).

### 7.3. Токен `__bs`

Stateless, проверяется без похода в хранилище:

```
v1 . issued_at . expires_at . class . ja4_hash[8] . ip_prefix_hash[4] . key_id . HMAC-SHA256
```

- Привязан к хешу JA4 и к /24 (/48 для IPv6). Смена TLS-стека или сети
  инвалидирует токен.
- TTL по классу: 30 мин – 24 ч. Ротация ключей через `key_id`, держатся два
  активных ключа.
- Cookie: `Secure; HttpOnly; SameSite=Lax; Path=/`.
- Отзыв массово — ротацией ключа, точечно — deny-листом `token_id` в Valkey
  (редко).
- Повторное использование одного токена с множества /24 или отпечатков
  (шаринг токенов между ботами) детектируется в аналитике, токен попадает в
  отзыв.

### 7.4. Не-HTML клиенты

API, XHR и мобильные клиенты не могут пройти интерстишиал. Для них
`challenge` деградирует в `throttle`, а затем в `block`, с JSON-ответом. API
можно защищать API-ключами (ключ лимита) или токеном, полученным при
навигации на сайт (SPA).

## 8. Rate limiting

### 8.1. Модель

- Алгоритм — **GCRA** (одна метка времени на ключ, ровная выдача, поддержка
  burst).
- Ключ — составной, задаётся в политике: `ip`, `ip_prefix`, `asn`, `fp`
  (JA4 + H2-fp), `session` (токен `__bs`), `header:<name>` (API-ключ), `jwt:sub`,
  а также комбинации вроде `fp+path_group`.
- Лимит зависит от класса: у `human` с токеном самый мягкий, у `suspicious`
  ниже, `bot` — минимальный или 0.
- Ответ при превышении: 429 с `Retry-After` и заголовками `RateLimit` и
  `RateLimit-Policy`.

### 8.2. Режимы

| Режим        | Как работает                                                        | Когда                         |
|--------------|---------------------------------------------------------------------|-------------------------------|
| `local`      | шард GCRA в памяти воркера (ключ хешируется на воркер)              | один узел, всё по умолчанию   |
| `synced`     | локально + каждые 100–250 мс дельты в Valkey и чтение глобального значения | несколько узлов, погрешность ±5–10 % допустима |
| `strict`     | атомарный GCRA в Valkey (Lua) синхронно на запрос                   | логин, оплата, регистрация    |

Если Valkey недоступен, `synced` и `strict` деградируют до `local`, а не
отказывают в обслуживании.

### 8.3. Защита самого шлюза

- Лимиты одновременных соединений и новых хендшейков на IP и /24 до TLS
  (TLS — самая дорогая часть).
- Таймауты: хендшейк 5 с, заголовки 10 с, idle 60 с, минимальная скорость тела.
- Лимиты H2: `MAX_CONCURRENT_STREAMS`, защита от rapid reset и flood
  SETTINGS/PING/CONTINUATION.

## 9. Политики и конфигурация

### 9.1. Источники

1. `bot-shield.yaml` — глобальные настройки, именованные политики, списки,
   правила CEL.
2. Docker-лейблы `botshield.*` на контейнерах — выбор политики и оверрайды
   по хосту.
3. `admin/api` — оперативные allow/deny с TTL, хранятся в Valkey или локальном
   файле.

Слияние: YAML-дефолт → политика из лейблов → оверрайды YAML по хосту →
оперативные списки. Результат — неизменяемый снапшот, который атомарно
подменяется у воркеров (RCU).

### 9.2. Привязка лейблов к хостам

Хосты контейнера определяются так:

1. `botshield.hosts=a.example.com,b.example.com`, если задан явно;
2. иначе разбором `Host(...)` и `HostSNI(...)` из
   `traefik.http.routers.*.rule` того же контейнера;
3. хосты, не найденные ни так, ни так, получают `default`.

### 9.3. Схема лейблов

```yaml
labels:
  botshield.policy: strict              # default | relaxed | strict | api | passthrough | off
  botshield.mode: enforce               # shadow | enforce
  botshield.ratelimit.default: "60/m burst=30 key=fp"
  botshield.ratelimit.api: "path=/api/* 20/s burst=40 key=session,ip_prefix"
  botshield.ratelimit.login: "path=/login 5/m key=ip mode=strict"
  botshield.challenge.paths: "/search*,/catalog/*"
  botshield.ai_crawlers: block          # allow | block
  botshield.honeypot.paths: "/wp-login.php,/.env"
```

### 9.4. Фрагмент `bot-shield.yaml`

```yaml
listen:
  http: ":80"
  https: ":443"
traefik:
  acme_json: /traefik/acme.json
  upstream_https: 127.0.0.1:8443
  upstream_http: 127.0.0.1:8080
  docker_socket: /var/run/docker.sock
mode: shadow                            # глобально, хост может переопределить
policies:
  default:
    thresholds: { suspicious: 30, bot: 70 }
    actions:   { suspicious: challenge, bot: block }
    ratelimit:
      - { key: fp, rate: 120/m, burst: 60, class: [human] }
      - { key: ip_prefix, rate: 30/m, class: [suspicious] }
  api:
    actions: { suspicious: throttle, bot: block }   # без интерстишиала
rules:
  - name: datacenter-no-token
    expr: 'net.asn_type == "datacenter" && !token.valid && score >= 20'
    action: challenge
lists:
  known_scrapers: file:///etc/bot-shield/lists/scrapers.txt
challenge:
  cookie: __bs
  path_prefix: /__bs/
  keys: file:///etc/bot-shield/keys.json
storage:
  valkey: ""                            # пусто = только локальное состояние
events:
  nats: nats://127.0.0.1:4222
  sample_allow: 0.05                    # allow сэмплируются, остальное — 100 %
```

## 10. Данные, аналитика, приватность

### 10.1. События

Два типа, JSON в NATS (`<prefix>.conn`, `<prefix>.req`), схема ClickHouse —
`deploy/clickhouse/schema.sql`:

- **conn** — при закрытии соединения: `ts_ms, instance, conn_id, listener,
  ip_prefix, ip_hash, route, reason, duration_ms, bytes_in, bytes_out,
  requests, sni, tls_version, alpn_offered, alpn, ja4, ja4_r, tcp_fp, ja4t,
  h2_fp`. Отправляется для всех маршрутов, включая reject.
- **req** — на каждый увиденный HTTP-запрос: `ts_ms, instance, conn_id, seq,
  ip_prefix, ip_hash, http_version, method, host, path_group, header_fp,
  header_names[], pseudo_order, has_cookie, has_referer, ja4h` + отпечатки
  соединения + `user_agent, accept*, sec_ch_ua*, sec_fetch_*`.

Пустые поля не передаются. С M2 добавятся `score, class, reasons[], action,
would_action`; с M3 — поля rate limit; ASN/страна — с IP-базами.

Сериализация — JSON (ADR-010): ClickHouse читает его NATS engine без
промежуточного сервиса. В ClickHouse события лежат в `MergeTree` с
партиционированием по дню, рядом — почасовая агрегация по отпечаткам
(`fp_hourly`) для кластеризации.

### 10.2. Хранение

| Данные                      | Срок        |
|-----------------------------|-------------|
| Сырые события               | 14 дней     |
| Агрегаты (час × хост × fp)  | 180 дней    |
| Библиотека отпечатков       | бессрочно, версионируется |

### 10.3. Приватность

- Полный IP в долговременное хранилище не пишется: только префикс и хеш с
  солью, которая ротируется.
- Сигналы JS-челленджа хешируются на клиенте, сырые значения canvas и WebGL не
  передаются.
- Query string не логируется, только `path_group` (нормализованный путь).
- Есть процедура удаления данных по запросу (по хешу IP или токену). Это
  требование GDPR и 152-ФЗ.

### 10.4. Петля улучшения

1. Кластеризация по (`ja4`, `h2_fp`, `ja4h`, `ua_family`): новые кластеры с
   высокой долей поведенческих аномалий попадают в кандидаты.
2. Кандидаты разбираются вручную через UI и `admin/api`, затем попадают в
   библиотеку отпечатков или в правила.
3. Обновление библиотеки — версионированный файл, который шлюз применяет
   горячей перезагрузкой.

## 11. Отказоустойчивость

- **Fail-open** (ADR-012). Небольшой watchdog (systemd unit) проверяет
  `/__bs/health` на loopback. После N неудачных проверок он переключает
  nftables-правило, и :443/:80 перенаправляются прямо в Traefik
  (`127.0.0.1:8443`/`8080`). После восстановления правило снимается.
- **Внутренние ошибки.** Исключение или таймаут в скоринге дают `allow` с
  `X-Bot-Reasons: internal_error` и метрику. Запрос не теряется.
- **Зависимости.** Недоступность Valkey, NATS или ClickHouse не влияет на
  обслуживание: лимиты становятся локальными, события сбрасываются с
  метрикой `events_dropped`.
- **Перезапуск без потерь.** Новая версия стартует с `SO_REUSEPORT`, старая
  перестаёт принимать соединения и дорабатывает текущие (graceful drain до 30 с).
- **Несколько узлов** (когда понадобится): два инстанса bot-shield + Traefik за
  keepalived/VRRP, состояние лимитов через Valkey, ключи токенов общие.

## 12. Наблюдаемость и эксплуатация

- **Метрики** (Prometheus, `:9900` на loopback): RPS по хосту и действию,
  распределение скоров, причины, латентность по стадиям (handshake, signals,
  score, upstream), хендшейки в секунду, срабатывания лимитов, состояние
  `acme.json`, возраст снапшота конфигурации, потерянные события.
- **Логи**: структурированный JSON, по умолчанию только не-`allow`.
- **Трассировка решения**: `GET /decisions/{request_id}` в `admin/api`
  показывает сигналы, веса, сработавшие правила и итог.
- **Деплой**: docker-compose рядом с Traefik (`network_mode: host`, монтируются
  `acme.json` read-only и `docker.sock` read-only).
- **Безопасность шлюза**: процесс без root (`CAP_NET_BIND_SERVICE`), ключи
  токенов — в файле с правами 0600, `admin/api` — только unix-сокет, разбор
  ClientHello, H1 и H2 покрыт фаззингом (libFuzzer) в CI.

## 13. Миграция с «чистого» Traefik

1. Развернуть NATS и ClickHouse (опционально, но для калибровки желательно).
2. Запустить bot-shield на временных портах (`:10443`) в `mode: shadow` и
   проверить вручную: сертификаты подхватываются, хосты из лейблов определены,
   WebSocket работает.
3. В Traefik включить `proxyProtocol.trustedIPs` и перенести entrypoint'ы на
   loopback (`deploy/traefik.yml`); bot-shield перевести на :80/:443. Это делается одним
   перезапуском, простой — секунды.
4. Включить watchdog и fail-open.
5. Одна–две недели в shadow mode: разбирать `would_action`, калибровать пороги
   и профили, собирать allowlist (мониторинг, партнёры).
6. Включать `enforce` по одному хосту, начиная с самых скрепящихся.
7. Хосты с gRPC или специфичными протоколами пометить
   `botshield.policy=passthrough`, пока их не поддерживает upstream (ниже).

### Статус M0

Сделано (код в `src/`, тесты в `tests/`):

- `net/classifier` + `tls/client_hello` — разбор ClientHello (в т. ч. разбитого
  на несколько TLS-записей и TCP-сегментов) и решение terminate / passthrough /
  reject. Поля для JA4 (cipher suites, расширения, группы, sig_algs, версии)
  уже собираются.
- `tls/cert_store` + `tls/acme_watcher` — загрузка `acme.json`, индекс по
  точным именам и wildcard, при дублях побеждает более поздний `notAfter`,
  битый файл не сбрасывает старые сертификаты.
- `net/prefixed_stream` — TLS-хендшейк поверх уже прочитанного ClientHello.
- `server/connection` — passthrough с half-close, терминация, повторный TLS до
  Traefik с тем же SNI и ALPN, PROXY v2, тайм-ауты (ClientHello, хендшейк,
  connect, idle).
- `server/gateway` — воркеры thread-per-core с `SO_REUSEPORT` (на macOS —
  один воркер), `TCP_SAVE_SYN` на Linux (SYN пока только считается),
  `/metrics` и `/health`, graceful drain по SIGTERM.
- Тесты: 40 юнит-тестов (GoogleTest) и сквозной `tests/e2e/run_e2e.py`
  (15 сценариев против фейкового Traefik с проверкой PROXY v2).

Отложено осознанно: `splice(2)`, пул и HTTP-aware прокси (M2), fail-open
watchdog (M5), лимиты соединений на IP (M3), HTTP/2 к gRPC-хостам (пока
`passthrough_hosts`).


### Статус M1

Сделано:

- `fp/tcp_syn` — разбор сохранённого SYN (IPv4/IPv6), свой `tcp_fp`.
- `fp/ja4` — JA4 и JA4_r, сверены с эталоном FoxIO.
- `fp/h1_tap`, `fp/h2_tap` — пассивное чтение HTTP/1.x и HTTP/2 (включая
  CONTINUATION, padding, PRIORITY, динамическую таблицу HPACK), Akamai `h2_fp`.
- `fp/http_fingerprint` — свой `header_fp`.
- `fp/foxio/` — JA4T и JA4H за опцией `BOT_SHIELD_FOXIO` (ADR-014).
- `events/` — JSON-события `conn` и `req`, IP только префиксом и HMAC-хешем,
  путь без query с нормализацией (`/items/:n`), замена невалидного UTF-8.
- `events/nats_publisher` — свой NATS-клиент: отдельный поток, ограниченная
  очередь с отбрасыванием, пакетная запись, PING/PONG, переподключение с
  backoff; метрики `events_total`, `nats_connected`, `nats_reconnects`.
- `deploy/clickhouse/schema.sql` — NATS engine → MergeTree (14 дней) и
  `fp_hourly` (180 дней); проверено на ClickHouse 25.8 + NATS 2.11.
- Тесты: 70 юнит-тестов, e2e с фейковым NATS (события HTTP/1.1, HTTP/2,
  plain HTTP, passthrough, reject; нет query и полных IP).


### Статус M2 (часть 1: прокси)

Сделано (`src/proxy/`):

- `h2_server` — HTTP/2 к клиенту на nghttp2; Akamai-отпечаток строится из
  тех же кадров (`fp/h2_fingerprint`), отдельная пассивная прослушка больше
  не нужна.
- `h1_server` — HTTP/1.x к клиенту на llhttp: keep-alive, pipelining по
  очереди, потоковые тела (Content-Length и chunked), `100-continue`,
  ответы с Content-Length / chunked (+ трейлеры) / до закрытия для 1.0,
  лимит заголовков 64 КБ (431), дедлайн на заголовки 30 с.
- WebSocket и другие Upgrade — отдельное HTTP/1.1-соединение к Traefik,
  после `101` — прозрачная пересылка.
- `h2_upstream` + `upstream_pool` — пул HTTP/2 к Traefik на воркер, ключ —
  SNI клиента, до `traefik.pool_size` соединений, очередь на время
  установки, idle-закрытие, корректный drain при остановке.
- `exchange` — пара запрос/ответ между сторонами; ручное управление
  окнами HTTP/2 (`consume` после фактической передачи), поэтому медленная
  сторона притормаживает быструю, а буферы ограничены.
- Заголовки: вырезаются hop-by-hop, `X-Forwarded-*`, `X-Real-IP`,
  `Forwarded`, `X-Bot-*` от клиента; выставляются свои `X-Forwarded-For`,
  `X-Real-IP`, `X-Forwarded-Proto/Host/Port`.
- Ответы шлюза: `502` при недоступном Traefik, `405` на CONNECT, `400/431`
  на битые запросы — с пометкой `local` в событиях.
- События `req` теперь отправляются по завершении и содержат `status`,
  `duration_ms`, `response_bytes`, `local`.
- Тесты: юнит-тесты сообщений и Exchange; e2e против собственного
  HTTP/2-апстрима (`tests/e2e/fake_upstream.cc`) — загрузки/выгрузки
  3–8 МБ, pipelining, трейлеры, WebSocket, 502, 50 параллельных запросов;
  ручная проверка с Traefik v3.5 + whoami (HTTP/1.1, HTTP/2, WebSocket,
  passthrough с PROXY, реальный IP).

Ограничения: HTTP/2 extended CONNECT (WebSocket поверх HTTP/2) не
объявляется — браузеры открывают для WebSocket отдельное HTTP/1.1-соединение;
серверный push не поддерживается (Traefik его не использует).

## 15. ADR

Формат: контекст → решение → альтернативы → последствия.

### ADR-001. TLS-фронт перед Traefik

- **Статус:** принято.
- **Контекст.** Много сайтов уже работают за Traefik (docker-лейблы, ACME).
  Основной метод — отпечатки TCP, TLS и HTTP/2, для которых нужны сырой SYN,
  ClientHello и кадры H2. Их видит только тот, кто первым принимает
  соединение и терминирует TLS.
- **Решение.** bot-shield слушает :80/:443, терминирует TLS и проксирует в
  Traefik, который переезжает на loopback.
- **Альтернативы.**
  - *ForwardAuth в Traefik*: тривиально встраивается, но шлюз не видит TLS,
    H2 и TCP, а заголовки приходят переупорядоченными и канонизированными.
    Основной метод теряется. Оставлен как возможный «лёгкий» режим.
  - *Плагин Traefik (Yaegi)*: нет доступа к сырому ClientHello и кадрам H2.
  - *L4-прослушка перед Traefik + ForwardAuth*: ForwardAuth не передаёт порт
    источника, поэтому соединение невозможно надёжно сопоставить с запросом
    (особенно за NAT). Нет H2-отпечатков.
  - *Заменить Traefik*: теряются docker-провайдер и лейблы, миграция всех
    сайтов.
- **Последствия.** Полный набор сигналов. Шлюз становится критическим звеном,
  поэтому нужен fail-open (ADR-012). Появляются двойной TLS (ADR-004) и
  зависимость от формата `acme.json` (ADR-003).

### ADR-002. Data plane на C++20, thread-per-core

- **Статус:** принято.
- **Контекст.** Горячий путь: TLS, разбор H1/H2, скоринг; цель — ≤ 2 мс p99 и
  десятки тысяч RPS. Нужен низкоуровневый доступ к ClientHello, сокетным
  опциям и кадрам H2.
- **Решение.** C++20 (Google C++ Style, clang-format). Asio (standalone) с
  корутинами C++20, по воркеру на ядро с `SO_REUSEPORT`, без общего
  изменяемого состояния. Библиотеки: BoringSSL, llhttp, nghttp2, cel-cpp,
  ONNX Runtime (позже), hiredis/redis-plus-plus для Valkey, nats.c.
  ClientHello разбирается собственным парсером до передачи в BoringSSL через
  memory BIO (нужен в любом случае для L4-классификации).
- **Альтернативы.**
  - *Rust (Pingora)*: безопасность памяти, но к сырому ClientHello и кадрам
    H2 пришлось бы пробиваться через абстракции. Выбор в пользу C++ сделан по
    предпочтению автора.
  - *Go*: GC-паузы и необходимость форкать `crypto/tls` и `x/net/http2`.
  - *Seastar*: мощно, но тяжёлая зависимость и своя экосистема. Можно
    вернуться к нему, если Asio упрётся в производительность.
  - *io_uring напрямую*: возможная оптимизация позже, за абстракцией
    транспорта.
- **Последствия.** Высокая производительность и контроль. Риск ошибок памяти
  в парсерах снижается фаззингом, ASan и UBSan в CI и минимальной
  поверхностью собственного парсинга.

### ADR-003. Сертификаты читаются из `acme.json` Traefik

- **Статус:** принято.
- **Контекст.** Traefik уже выпускает и продлевает сертификаты для всех
  сайтов. Дублировать ACME — значит рисковать лимитами Let's Encrypt и
  гонками.
- **Решение.** bot-shield монтирует `acme.json` только для чтения, следит за
  ним через inotify и атомарно подменяет хранилище сертификатов. Челленджи
  ACME (HTTP-01 и TLS-ALPN-01) пробрасываются в Traefik. SNI без сертификата
  уходит в passthrough.
- **Альтернативы.**
  - *Свой ACME в bot-shield*: независимость от Traefik, но дублирование и
    конфликт за HTTP-01.
  - *Сертификаты через файловый провайдер*: потребовал бы перестройки
    существующей схемы.
- **Последствия.** Нулевая настройка сертификатов. Зависимость от формата
  `acme.json` (стабилен много лет; покрывается тестами на фикстурах разных
  версий Traefik). Сертификаты из других провайдеров Traefik (file provider)
  подключаются отдельным источником — каталогом PEM.

### ADR-004. Повторное шифрование до Traefik вместо plain HTTP

- **Статус:** принято.
- **Контекст.** Роутеры висят на `websecure` с `tls=true`. Перевод на
  plain-HTTP entrypoint потребовал бы правок лейблов на всех контейнерах.
- **Решение.** Upstream в Traefik — TLS на loopback с тем же SNI и `Host`, пул
  keep-alive соединений (новых хендшейков почти нет). HTTP/1.1 на старте
  (включая WebSocket upgrade), HTTP/2 — на этапе M6.
- **Альтернативы.** *Отдельный plain entrypoint `shielded`* — дешевле по CPU,
  но требует правок лейблов. Остаётся оптимизацией на будущее.
- **Последствия.** Немного больше CPU: симметричное шифрование на
  переиспользуемых соединениях — единицы процентов. gRPC до появления H2
  upstream идёт через `policy=passthrough`.

### ADR-005. Local-first rate limiting на GCRA

- **Статус:** принято.
- **Контекст.** Синхронный поход в Redis на каждый запрос добавляет задержку
  и делает лимиты точкой отказа. Точный глобальный лимит нужен лишь на
  немногих маршрутах.
- **Решение.** GCRA в памяти воркера по умолчанию, режим `synced` с
  периодической синхронизацией дельт и режим `strict` с атомарным Lua в
  Valkey только для явно помеченных маршрутов. При отказе Valkey всё
  деградирует до `local`.
- **Альтернативы.** *Только централизованный счётчик* — проще и точнее, но
  медленнее и хрупче. *Token bucket* — эквивалентен по возможностям, но
  хранит два значения на ключ вместо одного.
- **Последствия.** Погрешность ±5–10 % на нескольких узлах в `synced`, что
  приемлемо для антибота.

### ADR-006. Self-hosted, один владелец

- **Статус:** принято.
- **Контекст.** Шлюз защищает собственные сайты владельца.
- **Решение.** Нет тенантов, квот и изоляции. Единый конфиг, единый набор
  ключей. Хост — основная единица политики.
- **Альтернативы.** *Multi-tenant* — отвергнут как преждевременный.
- **Последствия.** Модель данных и конфиг сильно проще. Если понадобится
  мультитенантность, ключом будет `tenant_id` поверх `host`, без переделки
  горячего пути.

### ADR-007. Пассивные отпечатки + JS + PoW, stateless-токен

- **Статус:** принято.
- **Контекст.** Одни пассивные сигналы слабы против настоящих headless-
  браузеров. Капчи портят UX, сторонние сервисы добавляют внешнюю
  зависимость.
- **Решение.** Пассивные сигналы по умолчанию. Невидимый JS-челлендж с PoW
  при подозрении. Результат — HMAC-токен, привязанный к JA4 и подсети, без
  серверного состояния. Капча — плагином, выключена.
- **Альтернативы.** *Только пассивные* — дешевле, но слабее. *Серверные
  сессии в Valkey* — точный отзыв, но зависимость от хранилища в горячем пути.
  *Мобильный SDK* — позже.
- **Последствия.** API-клиенты не проходят интерстишиал, для них отдельная
  деградация (раздел 7.4). Скрипт челленджа нужно поддерживать в гонке с
  обходами: версионируется и обфусцируется при сборке.

### ADR-008. Правила на CEL

- **Статус:** принято.
- **Контекст.** Нужен язык правил, который безопасно выполнять в горячем
  пути: без циклов, с предсказуемой стоимостью, проверкой типов при загрузке.
- **Решение.** CEL (`cel-cpp`). Правила компилируются при загрузке
  конфигурации, ошибки отвергают снапшот целиком (старый остаётся активным).
- **Альтернативы.** *Lua* — гибко, но тьюринг-полный, сложнее ограничить
  время. *Свой DSL* — затраты на парсер и инструменты.
- **Последствия.** Зависимость от `cel-cpp` (и через неё от Abseil и
  protobuf). Нужен бенчмарк стоимости вычисления правил.

### ADR-009. Valkey опционален, состояние в памяти по умолчанию

- **Статус:** принято.
- **Контекст.** На старте — один узел. Внешнее хранилище для одного узла даёт
  только новую точку отказа.
- **Решение.** Всё состояние в памяти. Valkey подключается при ≥ 2 узлах или
  для `strict` rate limit.
- **Альтернативы.** *Redis* — лицензионно менее удобен, протокол тот же.
  *Gossip между узлами* — сложнее, отложено.
- **Последствия.** После рестарта локальное состояние (окна, счётчики,
  deny-кеш) обнуляется. Это приемлемо: оно короткоживущее, а токены
  stateless.

### ADR-010. События: NATS JetStream → ClickHouse

- **Статус:** принято.
- **Контекст.** Аналитика и кластеризация требуют всех не-`allow` событий и
  сэмпла `allow`, а горячий путь не должен от этого зависеть.
- **Решение.** Неблокирующая отправка в NATS из отдельного потока с
  ограниченным буфером; при переполнении события сбрасываются с метрикой.
  Клиент свой, минимальный (core-протокол: CONNECT/PUB/PING/PONG), а не
  `nats.c`. События — JSON: ClickHouse читает их NATS engine напрямую.
  JetStream-поток на тех же subject'ах можно включить на сервере для
  буферизации и повторного чтения другими потребителями.
- **Альтернативы.** *Kafka* — избыточна для одного владельца. *Прямая вставка
  в ClickHouse* — нужна своя буферизация и ретраи в шлюзе.
- **Последствия.** Две дополнительные сущности в инфраструктуре; обе
  опциональны для работы шлюза. NATS engine ClickHouse подписан на core
  NATS: пока ClickHouse лежит, события теряются (это аналитика, не учёт).
  JSON больше бинарных форматов, но при текущих объёмах это не узкое место.

### ADR-011. HTTP/3 на входе отложен

- **Статус:** принято.
- **Контекст.** Если Traefik анонсирует `Alt-Svc: h3`, браузеры уходят на
  QUIC (UDP/443) мимо TCP-фронта.
- **Решение.** На v1 bot-shield вырезает `Alt-Svc` из ответов, а HTTP/3 в
  Traefik выключается (или UDP/443 закрывается). Поддержка QUIC с
  отпечатками transport params — этап M6.
- **Последствия.** Клиенты используют HTTP/2 — незаметно для пользователей,
  без потери защиты.

### ADR-012. Fail-open через watchdog и nftables

- **Статус:** принято.
- **Контекст.** bot-shield стоит перед всеми сайтами. Его отказ не должен
  означать их отказ.
- **Решение.** Отдельный watchdog проверяет здоровье шлюза и при отказе
  включает nftables-редирект :80/:443 → Traefik на loopback. Внутренние
  ошибки скоринга превращаются в `allow`.
- **Альтернативы.** *Fail-closed* — неприемлемо для владельца сайтов.
  *Только `Restart=always`* — не защищает от зависания без падения.
- **Последствия.** Во время отказа защиты нет, но сайты доступны. Переключение
  видно в метриках и алертах.


### ADR-013. M0: TLS-туннель до Traefik и PROXY protocol v2

- **Статус:** заменено ADR-015 (действовало на этапах M0–M1).
- **Контекст.** Для M0 нужно терминировать TLS и сохранить все возможности
  сайтов: HTTP/1.1, HTTP/2, WebSocket, длинные стримы. Полноценный HTTP-прокси
  (llhttp и nghttp2, перекодирование кадров, подстановка заголовков) нужен
  только к M2, когда появятся решения на уровне запроса.
- **Решение.** После хендшейка с клиентом шлюз открывает к Traefik отдельное
  TLS-соединение с тем же SNI, предлагает ровно тот ALPN, который выбрал
  клиент, и копирует расшифрованные байты в обе стороны. Реальный адрес
  клиента передаётся заголовком PROXY protocol v2 в начале каждого
  upstream-соединения. Если Traefik выбрал другой ALPN, соединение
  закрывается с метрикой `alpn_mismatches`.
- **Альтернативы.**
  - *Сразу HTTP-aware прокси* — больше кода до первых сигналов. Отложен до
    M2, где он действительно нужен.
  - *`forwardedHeaders` вместо PROXY* — требует вставки заголовков, то есть
    разбора HTTP. Невозможно в туннеле.
- **Последствия.** Одно upstream-соединение и один локальный TLS-хендшейк на
  каждое клиентское соединение, без переиспользования. На loopback это доли
  миллисекунды, но при большом числе коротких соединений — заметный CPU;
  уходит вместе с туннелем в M2. Заголовки `X-Bot-*` до M2 не передаются.


### ADR-014. Свои отпечатки TCP/HTTP, JA4T/JA4H — отдельным модулем

- **Статус:** принято.
- **Контекст.** JA4 (TLS) распространяется под BSD-3. JA4T и JA4H — под
  FoxIO License 1.1: бесплатно для защиты своих систем, но монетизация
  (продажа продукта или сервиса с ними) требует лицензии FoxIO. При этом
  они совместимы с внешними базами отпечатков.
- **Решение.** Основа скоринга и библиотеки — свои форматы без ограничений:
  `tcp_fp`, `header_fp` и открытый Akamai-формат `h2_fp`. JA4 считается
  всегда. JA4T и JA4H живут в `src/fp/foxio/` и собираются только с
  `-DBOT_SHIELD_FOXIO=ON` (по умолчанию включено, пока шлюз защищает свои
  сайты); они пишутся в события дополнительными полями.
- **Альтернативы.** *Только JA4+* — проще, но привязывает продукт к
  лицензии. *Только свои форматы* — теряется совместимость с внешними базами.
- **Последствия.** Сборка с `BOT_SHIELD_FOXIO=OFF` не содержит кода JA4+
  (проверено: 0 символов `foxio::` в бинарнике). Правила и библиотека
  отпечатков не должны зависеть от `ja4t`/`ja4h` как от единственного
  признака.


### ADR-015. Полный HTTP-прокси с пулом HTTP/2 к Traefik

- **Статус:** принято, заменяет ADR-013.
- **Контекст.** Для решений по запросам (скоринг, блок, челлендж, `X-Bot-*`)
  шлюз должен понимать HTTP и уметь отвечать сам. Туннель «соединение в
  соединение» этого не даёт, а TLS-хендшейк к Traefik на каждое клиентское
  соединение тратит CPU.
- **Решение.** Шлюз сам говорит HTTP/1.1 и HTTP/2 с клиентом и ходит в
  Traefik через пул HTTP/2-соединений на воркер (ключ — SNI, мультиплексирование
  потоков). Реальный адрес клиента — в `X-Forwarded-For` / `X-Real-IP`
  (Traefik доверяет им по `forwardedHeaders.trustedIPs`); те же заголовки
  от клиента вырезаются. Passthrough и порт 80 по-прежнему с PROXY v2.
  WebSocket — отдельным HTTP/1.1-соединением. Управление потоком сквозное:
  WINDOW_UPDATE отправляется только после того, как байты ушли дальше.
- **Альтернативы.**
  - *Переписывающий туннель* (1:1 соединения, правка заголовков в потоке,
    перекодирование HPACK) — меньше кода и без правки Traefik, но на HTTP/2
    свой ответ клиенту можно дать только сбросом потока, а вставка страницы
    челленджа конфликтует с flow control.
  - *Пул HTTP/1.1 keep-alive* — проще, но ломает gRPC (трейлеры) и требует
    больше соединений.
- **Последствия.** В Traefik добавляется `forwardedHeaders.trustedIPs` на
  `websecure`. Шлюз становится полноценным HTTP-прокси: корректность
  HTTP-семантики (тела, трейлеры, 1xx, keep-alive) теперь на нём и покрыта
  e2e. gRPC-хосты можно убирать из `passthrough_hosts` после проверки.

## 16. Открытые вопросы

- Целевая нагрузка в цифрах (пиковый RPS, число хостов) — уточнить для
  нагрузочного теста M0.
- Источник IP-баз (ASN, датацентры, резидентные прокси): бесплатные
  (iptoasn, списки облаков) или коммерческие.
- Нужна ли инъекция `<script>` челленджа в HTML-ответы для невидимого сбора
  сигналов без интерстишиала. Требует разбора и переписывания тела ответа,
  стоит отдельно оценить.
- Мобильные приложения на тех же хостах: нужен ли SDK с App Attest и Play
  Integrity, или достаточно API-ключей и лимитов.
- Политика для AI-краулеров: блок, allow, или `402` с оплатой.
- Где запускать офлайн-задачи и UI: на том же хосте или отдельно.
